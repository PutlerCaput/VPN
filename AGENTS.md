# AGENTS.md

## Архитектура

- Telegram-бот на aiogram находится в `main.py` и `handlers/`. `services/` содержит интеграции с платёжными провайдерами и Hiddify Manager, биллинг и выдачу доступа. HTTP-сервер `webhook_server.py` на aiohttp обслуживает вебхуки и REST API в `api/`. В `db/` реализованы хранение в SQLCipher и доступ к БД через шлюз. [README проекта](README.md)
- `pwa/` и `tma/` — два клиента на React и Vite для веба и Telegram Mini App. `Dockerfile`, `docker-compose.yml` и `Caddyfile` содержат шаблоны приложения. В `deploy/xray/` находятся правила маршрутизации Xray и обновление геоданных. [Индекс документации](docs/README.md)
- `deploy/four_node/` содержит комплект для стенда. RU-1 передаёт TCP/443 через HAProxy в NL-1, RU-2 — в NL-2. VLESS REALITY завершается на выходах NL с независимыми парами ключей. Каждая цепочка требует своего клиентского профиля. Переключение клиента проверяй отдельно. [Схема и генератор](deploy/four_node/README.md)
- Состояние четырёх VPS устанавливай по свежему аудиту. `docs/ARCHITECTURE.md` описывает прежнюю схему, `docs/DEPLOYMENT_STATE.md` хранит исторические снимки. Для новых узлов используй актуальный регламент. [Регламент четырёх VPS](docs/FOUR_NODE_MIGRATION_2026-11-20.md)

## Работа с кодом и GitHub

- В рамках задачи можно самостоятельно исправлять код, запускать тесты, создавать коммиты в рабочей ветке, отправлять её на GitHub и открывать или обновлять PR к `main`. Сверяй базу с актуальным `main` и сохраняй существующие правки пользователя. Изменения в `main` проходят через PR. Мерж требует явного подтверждения владельца.
- Держи diff в рамках задачи. Перед отправкой проверь состав коммита и запусти `./scripts/secret_scan.sh`. В PR укажи причину, выполненные проверки и результаты. После открытия проверь CI и исправь сбои, вызванные изменением. [CI](.github/workflows/ci.yml)
- Репозиторий публичный. Храни вне Git и публичных обсуждений инвентарь и адреса VPS, `.env` со значениями, секреты, закрытые ключи SSH и age, дампы `docker inspect`, базы, бэкапы и клиентские ссылки. Для тестов используй фикстуры и тестовые ключи. [Правила хранения](docs/README.md) · [Проверка секретов](docs/SUBSCRIPTION_SECURITY_BOUNDARY.md)
- При изменениях подписок сохраняй изоляцию сегментов и выдачу контролируемой ошибки при сбое фильтрации. Доступ к необработанной подписке панели должен оставаться закрытым. Учётные данные из генератора четырёх узлов предназначены для стенда. Для платного запуска требуется проверенная выдача и отзыв доступа каждого пользователя на обоих NL-узлах. [Фильтрация подписок](docs/SUBSCRIPTION_SECURITY_BOUNDARY.md) · [Приёмка выпуска](docs/FOUR_NODE_RELEASE_READINESS.md)

## Тестирование

- Для Python используй 3.11, зависимости из `requirements-dev.txt` в локальной `.venv` и `make check` для Ruff, mypy, поиска секретов, Bandit, аудита зависимостей и pytest. `make test` запускает набор pytest. [Makefile](Makefile) · [Настройки Python](pyproject.toml)
- Для изменений веб-интерфейса запускай `npm ci` и `npm run build` в затронутом каталоге `pwa/` или `tma/`. CI использует Node.js 20 и собирает оба приложения. [CI](.github/workflows/ci.yml)
- Для генератора узлов запусти `python -m unittest discover -s tests -p 'test_four_node_*.py' -v`. При изменениях плана подписок или критериев готовности запусти соответствующие `tests/test_four_node_*.py` через pytest. Workflow четырёх узлов проверяет синтаксис Xray на закреплённом образе и обе конфигурации HAProxy. Исправность VPN подтверждай реальным клиентским подключением. [Проверки четырёх узлов](.github/workflows/four-node.yml)
- Тесты серверных скриптов, которым нужен root, запускай в одноразовом контейнере по образцу CI. Для платежей, базы и панели используй тестовые данные и изолированную среду. [CI](.github/workflows/ci.yml)

## SSH и развёртывание

1. Используй приватный инвентарь с подтверждёнными хостом, пользователем, портом и назначенным существующим ключом для каждого алиаса RU-1, RU-2, NL-1 и NL-2. Сверь отпечаток ключа хоста по доверенному каналу провайдера. Если инвентарь или ключ недоступен либо отпечаток отличается от доверенного, остановись и сообщи причину. [Первый доступ](docs/FOUR_NODE_MIGRATION_2026-11-20.md#phase-1--first-contact-requires-authenticated-ssh-or-provider-console)
2. Проверяй вход с `BatchMode=yes`, `IdentitiesOnly=yes`, `StrictHostKeyChecking=yes` и `UpdateHostKeys=no`, используя существующий `known_hosts`. При ошибке аутентификации зафиксируй её по алиасу и проверь назначение ключа по приватному инвентарю.
3. Начинай с аудита без изменений. Сверь версию ОС и ядра, ресурсы, время, SSH, Docker, Xray, HAProxy, слушающие TCP/UDP-порты, firewall и владельца TCP/443. Пользуйся `deploy/four_node/preflight.sh` для первичной диагностики и убирай адреса и чувствительные сведения из публикуемого вывода. [Первичная диагностика](deploy/four_node/preflight.sh)
4. Установка, обновление, перезапуск и любое изменение на VPS, а также изменения боевого DNS и платёжной конфигурации требуют явного подтверждения владельца. Перед согласованным развёртыванием сделай зашифрованную резервную копию и проверь восстановление. Зафиксируй текущие версии, конфигурации и правила firewall. Двигайся по одному узлу, начиная с NL-выходов. Проверь реальное подключение через каждую пару, ожидаемый выход и DNS. При сбое останови развёртывание и восстанови прежнее состояние затронутого узла по регламенту. [Резервные копии](docs/BACKUPS.md) · [Развёртывание и откат](docs/FOUR_NODE_MIGRATION_2026-11-20.md)

# Архитектура: вход → транзит → выход

Актуально на 17 ноября 2026 года (после PR #48 и #49: туннель `wg-vpn`, запасной порт
Hysteria2, conntrack 65536). Документ описывает, как сервис устроен сейчас, что добавлено
этим изменением (шардирование входов, закрытие панели, отпечаток `chrome`) и что ещё
предстоит сделать руками. Подробности по отдельным темам:

- [ANTI_CENSORSHIP_AUDIT.md](ANTI_CENSORSHIP_AUDIT.md): аудит устойчивости к блокировкам,
  разбор советов, план по шагам;
- [AMNEZIA_COMPARISON.md](AMNEZIA_COMPARISON.md): AmneziaWG, второй протокол;
- [VPN_ENTRIES.md](VPN_ENTRIES.md): входы в подписке, проброс на RU, туннель `wg-vpn`,
  второй RU-вход;
- [PANEL_LOCKDOWN.md](PANEL_LOCKDOWN.md): закрыть панель Hiddify и отделить сайт от IP VPN.

## 1. Схема

```
                 ┌──────────────── ВХОД (Россия) ────────────────┐
 Клиент в РФ ──► │ RU-1 45.138.157.65                             │
 (Hiddify,       │   TCP 443 2087 8443 2083 2085 ─DNAT─┐          │
  v2rayNG,       │   UDP 36099, UDP 443 ──DNAT─────────┼──┐       │
  AmneziaWG)     │   UDP 39051 44877 (AmneziaWG) ──────┼──┼──┐    │
                 │ RU-2 (план, другой хостер) — то же   │  │  │    │
                 └──────────────────────────────────────┼──┼──┼────┘
                          ТРАНЗИТ                       │  │  │
                 wg-vpn 10.205.0.1 ⇄ 10.205.0.2 ◄───────┘  │  │  TCP внутри WireGuard,
                 (UDP 51821 на RU, MTU 1420, MSS 1380)     │  │  MSS clamp
                 открытый интернет, UDP ◄──────────────────┘  │  Hysteria2 мимо туннеля
                 открытый интернет, UDP ◄─────────────────────┘  AmneziaWG
                 ┌──────────────── ВЫХОД (DE, Хельсинки, HOSTKEY) ─┐
                 │ 89.125.210.172                                  │
                 │  Hiddify Manager 14.2: VLESS REALITY (TCP, gRPC,│
 Клиент вне РФ ─►│   XHTTP) на 2443; Hysteria2+Salamander 36099/udp│──► интернет
 (прямой вход)   │  AmneziaWG 39051/44877 udp                      │
                 │  Caddy 80/443/8443: app.…, sub.…, panel.…       │
                 └─────────────────────────────────────────────────┘
 Плоскость управления: бот + PWA + Mini App (DE, Docker) ──wg-db──► база на RU (шлюз 8444)
                       бот ──► API Hiddify (выдача пользователей и подписок)
```

Почему так:

- **Вход в РФ.** Зарубежные адреса у мобильных операторов режут сильнее российских. Клиент
  подключается к российскому адресу, RU ничего не расшифровывает (REALITY и Hysteria2
  заканчиваются в DE), это чистый DNAT. Ключей на RU нет.
- **Транзит.** На открытом участке RU → DE обрывалась заметная доля TCP Reality (20 из 48
  в замере). Внутри туннеля `wg-vpn` — 48 из 48. UDP (Hysteria2, AmneziaWG) идёт мимо
  туннеля: он и так проходит, а лишняя инкапсуляция съедала бы MTU.
- **Выход.** Один сервер в DE держит Hiddify Manager и AmneziaWG. Отдельного «exit»-узла
  за ним нет: сейчас это лишнее звено и лишняя задержка.

## 2. Слои и их отказ

| Слой | Сейчас | Что ломается при блокировке | Резерв |
|---|---|---|---|
| Вход TCP | RU-1: 443, 2087, 8443, 2083, 2085 → DE:2443 через `wg-vpn` | заблокирован адрес RU-1 или его хостер | RU-2 (раздел 3), прямой DE:2443 (у части операторов не проходит) |
| Вход UDP | RU-1: 36099 и 443 → DE:36099 (Hysteria2) | оператор режет UDP/QUIC | TCP-входы, AmneziaWG |
| AmneziaWG | RU-1 → DE 39051/44877 | сигнатура WireGuard (обфускация AWG её прячет) | VLESS, Hysteria2 |
| Транзит | `wg-vpn` UDP 51821 | хостер RU режет WireGuard наружу | откат на прямой DNAT (`VPN_ENTRIES.md`) |
| Выход | DE 89.125.210.172 | адрес DE в чёрном списке целиком | входы через RU не зависят от доступности DE из РФ |
| Управление | бот, сайт, подписка на DE | домен сайта заблокирован, IP «засвечен» | раздел 6 (CDN/отдельный сервер) |

## 3. Второй российский вход (RU-2)

Цель: блокировка одного адреса или одного хостера не отключает никого. RU-2 — у **другого**
хостера (другая автономная система), с тем же набором пробросов. Пошагово —
[VPN_ENTRIES.md, «Второй вход в РФ (RU-2)»](VPN_ENTRIES.md#второй-вход-в-рф-ru-2). Коротко:

1. Свой туннель `wg-vpn2` RU-2 ⇄ DE (`10.206.0.1/30` ⇄ `10.206.0.2/30`).
2. На RU-2 тот же `scripts/ru_vless_relay.sh --apply` с `DE_TUNNEL_IP=10.206.0.2`
   (скрипт параметризован, его код не меняется), `scripts/ru_firewall.sh` и
   `scripts/net_tuning.sh`.
3. Адрес RU-2 в подписку: `scripts/vpn_entries.py --add RU2:443` (и другие порты/теги,
   как у RU-1).
4. С шардированием (раздел 4) RU-1 и RU-2 попадают в разные сегменты: пользователь видит
   один из них плюс общие входы.

## 4. Плоскость управления и шардирование конфигураций

Задача: если подписку одного пользователя разберут (сканер, «утёкшая» ссылка, купленный
аккаунт), блокировщик не должен узнать **все** входы сразу.

Как устроено (выключено по умолчанию, `ENTRY_SHARDING_ENABLED=false`):

- **Сегменты.** `ENTRY_SEGMENTS` — JSON «имя → адреса входов», например
  `{"ru-a": ["<RU-1>"], "ru-b": ["<RU-2>"]}`. `ENTRY_SHARED_HOSTS` — адреса, которые
  получает каждый (например, прямой DE). `ENTRY_SHARDING_STRICT=true` — вход на адресе,
  которого нет ни в одном списке, не получает никто.
- **Назначение.** Детерминированно: HMAC-SHA256 от Telegram id на ключе, выведенном из
  `JWT_SECRET` (без ключа соответствие не пересчитать). Первое назначение закрепляется в
  таблице `entry_segments` (источник `auto`), так что смена списка сегментов не перемешивает
  всех. Админ закрепляет вручную (`admin`):
  `docker exec -i node-rental-bot-1 python3 - --set <telegram_id> ru-b < scripts/entry_segments.py`.
  Автоматическая запись никогда не перезаписывает ручную.
- **Выдача.** При включённом флаге бот выдаёт ссылку `https://<ENTRY_SHARDING_BASE_URL или
  PUBLIC_BASE_URL>/api/v1/sub/<uuid>/` вместо прямой ссылки Hiddify. Обработчик скачивает
  подписку пользователя у Hiddify (с User-Agent его приложения, **без** ключа API), оставляет
  только входы его сегмента и общие, и отдаёт её. Понимает списки ссылок (обычные и base64,
  vless/trojan/hysteria2/tuic/ss/vmess), JSON sing-box и Xray; группы selector/urltest
  чистятся от удалённых узлов. Формат, который разобрать нельзя (Clash YAML), не
  пересылается: бот просит у панели список ссылок. Пустой результат — ошибка 503, а не
  пустая подписка: приложение сохраняет прежний рабочий профиль.
- **Изоляция.** Адрес другого сегмента не попадает в ответ ни в каком формате (тесты
  `tests/test_entry_sharding.py`). Заголовки панели пересылаются только из белого списка
  (трафик, интервал обновления, название), cookie и прочее — нет.
- **Против сбора (anti-parsing).** Все ограничения в памяти процесса, ничего не пишется:
  - адрес: 30 запросов за 10 минут (`SUB_RATE_PER_IP_10MIN`);
  - подписка: 20 скачиваний в час (`SUB_RATE_PER_USER_HOUR`);
  - неверный/чужой UUID: после 10 промахов за час (`SUB_MISSES_PER_IP_HOUR`) адрес
    получает 429 на час, даже с верным UUID (перебор);
  - одна подписка — не больше 12 разных адресов в сутки (`SUB_SOURCES_PER_USER_DAY`):
    ссылка, выложенная в чат или скормленная скрейперу, перестаёт отдаваться; адреса
    хранятся только как солёные хэши в памяти;
  - неизвестный UUID, неактивный пользователь и выключенный флаг отвечают одинаково (404).
- **Ограничение.** Пока прямой адрес подписки Hiddify (`sub.cyberdefency.com:8443`)
  открыт, старая ссылка отдаёт полный список. Изоляция полная, когда все перешли на новую
  ссылку и прямой адрес закрыт (раздел 5, шаг 4 в «Ручные шаги»).

Сопоставление с кодом:

| Что | Где |
|---|---|
| Настройки и проверки | `config.py` (`entry_sharding_*`, `entry_segments`, `sub_*`, `subscription_fingerprint`) |
| Сегменты, фильтр, отпечаток, `FanoutGuard` | `services/sharding.py` |
| Таблица `entry_segments`, методы | `db/database.py` (`ENTRY_SEGMENTS_SCHEMA`, `get/set/clear_entry_segment`, `entry_segment_counts`) |
| Обработчик `/api/v1/sub/{uuid}` | `api/routes.py` (`sharded_subscription`) |
| Ограничения запросов | `api/middleware.py` (`build_limiters`: `sub_ip`, `sub_user`, `sub_miss_ip`) |
| Скачивание подписки без ключа API | `services/hiddify.py` (`fetch_subscription`) |
| Какую ссылку выдаёт бот | `services/provisioning.py` (`_config_from`) |
| Админ-команды | `scripts/entry_segments.py` |
| Тесты | `tests/test_entry_sharding.py` |

База данных живёт на RU за шлюзом (`db/gateway.py`). Новые методы базы — это новые методы
шлюза: **шлюз на RU обновляется первым** (`db_gateway_install.sh --apply`), иначе бот
откажется к нему подключаться («the database gateway is older than this bot»). Так
устроено для любого изменения базы, см. `scripts/update_bot.sh`.

## 5. Защита от активного зондирования (anti-probing)

- **REALITY.** Чужой клиент без ключа получает настоящий TLS сайта-маскировки: сервер
  выглядит как этот сайт. Маскировку выбирать по `ANTI_CENSORSHIP_AUDIT.md`, п. 4.1
  (TLS 1.3 + h2 с этого сервера, не самые частые имена).
- **Отпечаток клиента `chrome`.** ClientHello клиента неотличим от Chrome. Задаётся в
  панели (раздел 7), бот может дополнительно проставить его в отфильтрованной подписке
  (`SUBSCRIPTION_FINGERPRINT=chrome`).
- **Hysteria2 с Salamander.** Пакеты без пароля обфускации выглядят как шум, сервер на
  них не отвечает.
- **Панель не видна из интернета.** `scripts/de_lockdown.sh` (ufw, только нужные порты) и
  allowlist на сайте панели в Caddy — [PANEL_LOCKDOWN.md](PANEL_LOCKDOWN.md).
- **Сайт не на IP VPN.** Сайт, Mini App и подписка — за CDN или на отдельном сервере
  (там же), чтобы домен сайта не указывал на выход VPN.
- **Одинаковые ответы.** `/api/v1/sub` отвечает 404 на всё «чужое»; служебные пути
  (`/metrics`, `/internal`) Caddy отдаёт 404.

## 6. Минимум журналов (zero-logs)

Что уже так:

- бот не хранит журналы подключений: `ACTIVITY_LOGGING_ENABLED=false` по умолчанию,
  `conn_logs` пустой; срок хранения и архив — `docs/RETENTION.md`;
- `/api/v1/sub` не пишет ни IP, ни UUID, ни ссылки; в журнале только сегмент и формат;
- в таблице `entry_segments` только имя сегмента, без адресов и IP;
- RU — чистый DNAT, журналов трафика там нет.

Рекомендуется (вручную, на серверах):

- Hiddify Manager: уровень журнала Xray/sing-box `warning` или `none`, журнал доступа
  (access log) выключить;
- Caddy: не включать `log` для `sub.…` и `app.…` (журнал доступа по умолчанию выключен,
  проверить, что его не добавили);
- journald на DE и RU: `SystemMaxUse=200M`, `MaxRetentionSec=7day`;
- AmneziaWG: не включать журнал рукопожатий;
- conntrack на RU хранит записи только пока живёт поток (таймауты по умолчанию).

## 7. Отпечаток `chrome` и gRPC + REALITY

Подписку формирует Hiddify, поэтому основное — настройки панели:

1. Отпечаток: `docker exec -i node-rental-bot-1 python3 - --fingerprint chrome <
   scripts/vpn_entries.py` (поле `fingerprint` у каждого адреса входа). В интерфейсе
   панели — настройка uTLS (fingerprint) = `chrome`.
2. gRPC + REALITY: в Hiddify Manager 14 — включить gRPC для REALITY в настройках
   протоколов; через RU он идёт тем же TCP-пробросом в `wg-vpn` (порты 443/2087/8443/
   2083/2085 → DE:2443). Отдельный вход на своём порту — `scripts/vless_transport.sh`
   (`VPN_ENTRIES.md`, шаг 2).
3. Проверка: обновить подписку в приложении; в ссылках VLESS — `fp=chrome`, есть профили
   `grpc`. Опись без секретов — `scripts/vpn_entries.py` без аргументов.

Подробнее — [VPN_ENTRIES.md, «Отпечаток chrome и gRPC + REALITY в Hiddify 14»](VPN_ENTRIES.md#отпечаток-chrome-и-grpc--reality-в-hiddify-14).

## 8. Ручные шаги для продакшена

Ничего из этого не применяется автоматически; код по умолчанию ведёт себя как раньше.

1. Подписать выпуск на телефоне (`bash ~/release_sign.sh`), потом обновить **шлюз базы на
   RU** (`db_gateway_install.sh --apply`) и только затем бота (`update_bot.sh`).
   Это нужно даже при `ENTRY_SHARDING_ENABLED=false`: в `Database` четыре новых метода, и
   новый бот не подключится к старому шлюзу. Если порядок нарушить (вручную или ежемесячным
   `node-update.timer`), `update_bot.sh` при `DATABASE_URL` лишь печатает `DB_REMOTE`,
   пересоздаёт бота, ждёт «healthy» до `HEALTH_TIMEOUT` (150 с) и сам возвращает прежний
   образ и `.env`: обновление не пройдёт, бот будет недоступен несколько минут. Само
   слияние PR и подпись ничего на серверах не меняют.
2. Отпечаток `chrome` и gRPC + REALITY в панели (раздел 7).
3. `scripts/de_lockdown.sh` (сначала без аргументов — отчёт), затем allowlist панели в
   Caddy (`PANEL_LOCKDOWN.md`).
4. RU-2 (раздел 3) — когда будет второй сервер.
5. Шардирование: задать `ENTRY_SEGMENTS`, `ENTRY_SHARED_HOSTS`, `ENTRY_SHARDING_ENABLED=true`
   (`update_bot.sh --set ...`), разослать пользователям новую ссылку (бот выдаёт её в
   «Подключить»), через 1–2 недели закрыть прямой адрес подписки Hiddify.
6. Сайт за CDN или на отдельный сервер (`PANEL_LOCKDOWN.md`, раздел 3).

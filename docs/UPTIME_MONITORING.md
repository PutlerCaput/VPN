# Внешний монитор доступности

Редакция от 9 ноября 2026. У сервиса один сервер и встроенный мониторинг, но
если упадёт весь сервер или сам бот, предупредить вас будет некому: тот, кто
следит, падает вместе с ним. Поэтому проверять нужно **снаружи**, с другой
машины.

## Что проверять

Бот отвечает на публичный адрес без входа и данных клиентов:

```
GET https://app.cyberdefency.com/healthz
```

Ответ, когда всё хорошо: HTTP 200 и тело

```json
{"status": "ok", "db": true}
```

Это доказывает, что отвечает Caddy, жив процесс бота и читается база. Это **не**
доказывает, что работает сам VPN-туннель, — это отдельная проверка с клиентом.

Если сервер лежит, бот не отвечает или база недоступна, монитор увидит либо
таймаут, либо ответ без `ok` — и пришлёт уведомление.

## Вариант A: бесплатный внешний сервис (рекомендую)

Подходит любой сервис мониторинга «HTTP(s) uptime» с бесплатным тарифом
(например, UptimeRobot, Better Stack, Hetrix — выбор за вами). Общие шаги
одинаковые:

1. Заведите аккаунт на почту, которую вы контролируете, включите на нём
   двухфакторную защиту. Этот аккаунт — ещё одна точка, где лежат ваши данные,
   держите его под замком.
2. Создайте монитор типа **HTTP(s)** на адрес
   `https://app.cyberdefency.com/healthz`.
3. **Проверка по слову (keyword):** если сервис это умеет, включите совпадение с
   текстом `ok`. Так монитор считает «работает», только когда в ответе есть
   `ok`, а не просто любой код 200 (страница ошибки тоже бывает 200).
4. **Интервал:** 5 минут достаточно.
5. **Порог уведомления:** оповещать после 2 неудач подряд, чтобы одна случайная
   сетевая заминка не будила вас зря.
6. **Канал уведомления:** почта работает надёжно. Телеграм-оповещение не
   привязывайте к боту сервиса — если он упал, он же и не напишет; используйте
   встроенный канал сервиса мониторинга или отдельного бота (Вариант B).

Проверьте, что оповещение приходит: на пару минут остановите веб-контейнер
(`docker stop node-rental-web-local-app-web`), дождитесь письма, затем снова
запустите (`docker start …`) — или просто поверьте первой реальной тревоге.

Замечание для РФ: такие сервисы доступны, письма приходят. Если не хотите
зависеть от зарубежного сервиса — Вариант B.

## Вариант B: своя проверка, без третьих лиц

Нужна любая **другая** всегда включённая машина (второй VPS, домашний
мини-сервер) — не этот сервер и не телефон, который спит. На ней по расписанию
(cron, раз в 5 минут) дёргайте адрес и при двух неудачах подряд шлите себе
сообщение через **отдельного** телеграм-бота (заведите его в @BotFather, это не
бот сервиса). Токен и ваш chat_id держите в файле с правами 600, не в коде.

Набросок проверки (подставьте свои токен и chat_id):

```bash
#!/usr/bin/env bash
# uptime_check.sh — запускать по cron раз в 5 минут на ДРУГОЙ машине.
set -uo pipefail
URL="https://app.cyberdefency.com/healthz"
STATE="/tmp/.cyberdefency-uptime"   # счётчик неудач между запусками
ALERT_BOT="ТОКЕН_ОТДЕЛЬНОГО_БОТА"   # не бот сервиса
CHAT_ID="ВАШ_CHAT_ID"

body="$(curl -fsS --max-time 15 "$URL" 2>/dev/null || true)"
if printf '%s' "$body" | grep -q '"status": *"ok"'; then
  rm -f "$STATE"                      # всё хорошо, счётчик сброшен
  exit 0
fi
fails=$(( $(cat "$STATE" 2>/dev/null || echo 0) + 1 ))
echo "$fails" > "$STATE"
# шлём тревогу один раз, на второй неудаче подряд
if [[ "$fails" == 2 ]]; then
  curl -fsS --max-time 15 \
    "https://api.telegram.org/bot${ALERT_BOT}/sendMessage" \
    --data-urlencode "chat_id=${CHAT_ID}" \
    --data-urlencode "text=⚠️ Cyberdefency: $URL не отвечает (${fails} раза подряд)" \
    >/dev/null || true
fi
```

Строка cron (раз в 5 минут): `*/5 * * * * /path/to/uptime_check.sh`.

## Что это НЕ заменяет

- Встроенные уведомления бота (аномалии трафика, состояние панели) — они про
  другое и остаются.
- Проверку, что оплаченная подписка выдаёт рабочее VPN-подключение, — это
  приёмка с клиентом, монитор `/healthz` её не делает.
- Резервные копии — монитор говорит, что сервер жив, а не что копия сделана.

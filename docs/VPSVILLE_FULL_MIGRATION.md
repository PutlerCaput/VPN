# Полный перенос Cyberdefency на VPSVILLE — исторический план

> **ВНИМАНИЕ: УСТАРЕЛО по состоянию на 20.11.2026.** Четыре новых VPS уже предоставлены владельцу, старые серверы больше не существуют. Ниже сохранены исторические оценки тарифов, ролей и этапов, составленные 19.11.2026. **Не запускать команды миграции со старых DE/RU и не использовать старые IP, тарифы и предположения о базе.** Актуальная схема RU-1→NL-1, RU-2→NL-2 и тестовый генератор находятся в [черновике PR #54](https://github.com/PutlerCaput/VPN/pull/54). Отсутствие SSH-доступа не позволяет подтвердить настройку новых VPS.

Дата исходного плана: 19.11.2026. Статус: архивный план, **не runbook для новых серверов**.

## Решение владельца (историческое)

Изначально предполагался перенос к VPSVILLE с параллельной работой прежних серверов. Это условие больше неактуально: владелец подтвердил, что прежних серверов нет. Новую систему необходимо собирать без предположения о доступности исходной инфраструктуры или резервных копий.

## Важный компромисс

VPSVILLE использует как минимум две собственные автономные системы: AS59504 и AS204916. Публичные BGP-данные показывают нидерландский префикс 45.142.208.0/24 в AS59504; AS204916 сейчас анонсирует российские префиксы. Это позволяет запросить разные ASN для части RU/NL узлов, но **не даёт независимости от самого VPSVILLE**: общий сбой провайдера, биллинга, аккаунта или его магистральной сети может затронуть все новые серверы. Не называть такую схему полностью независимой или гарантированно безотказной.

При заказе запросить:
- RU-1: по возможности IP из AS204916;
- RU-2: IP из AS59504, если VPSVILLE может назначить именно такой маршрут;
- NL-1 и NL-2: нидерландские IP, ожидаемо AS59504;
- фактический origin ASN каждого IP проверить после выдачи через RIPEstat/BGP. Нельзя выбирать ASN только по геолокации или названию тарифа.

AS204916 и AS59504 зарегистрированы на одну организацию LLC VPSVILLE; это разные ASN, но не разные операторы.

## Текущая система по последним эксплуатационным записям

- RU: RUVDS, Ubuntu 24.04, 1 GB RAM, 20 GB disk, публичный IP 45.138.157.65. Российский VPN relay (DNAT TCP 443/2087/8443 на DE), WireGuard DB tunnel и SQLCipher database gateway. После миграции БД на RU рабочая база и gateway находятся на RU.
- DE: HOSTKEY, Ubuntu 24.04.5, публичный IP 89.125.210.172. Здесь работают Telegram-бот, web/PWA/TMA, Hiddify Manager, Xray и Caddy. Hiddify Manager указан в эксплуатационном снимке как v0.8.4; фактическую версию повторно проверить непосредственно перед копированием.
- AmneziaWG \`amnezia-awg2\` на DE в старой инвентаризации обозначен как личный профиль владельца, а не абонентский сервер. Его переносить только если владелец продолжает им пользоваться. Его конфигурация не включена в стандартный backup проекта.

Эти сведения взяты из \`docs/DEPLOYMENT_STATE.md\`, \`docs/WEB_DEPLOYMENT.md\`, \`docs/RU_DATABASE_CUTOVER.md\` и \`docs/BACKUPS.md\`; это исторический снимок, перед миграцией требуется свежая read-only инвентаризация.

(14 520 ₽/год).** Все цифры — опубликованные тарифы VPSVILLE на дату проверки, не итоговая корзина. Дополнительные IPv4, backup/snapshot, DDoS-защита и другие опции могут оплачиваться отдельно; подтвердить до заказа.

**Обоснование и ограничения:**
- RU-1: 2 GB RAM достаточно как стартовый лимит для лёгкой SQLCipher БД, Python gateway, WireGuard и NAT, если объём данных/записи и CPU не превышают план; 1 vCPU может стать узким местом при шифровании большого трафика. Нужны мониторинг p95, CPU steal, OOM, диска и WAL, ежедневный зашифрованный backup.
- RU-2: Camp 1 GB/15 GB только для iptables/nftables, WireGuard, SSH и базового мониторинга. Не устанавливать на него Docker/Hiddify, базу, бота, журналы пользовательского трафика. Обязательно протестировать UDP throughput и memory pressure; при OOM/packet loss обновить до Farm+. Camp без «+» предназначен для РФ, не для Нидерландов.
- NL-1: 4 GB RAM, 2 vCPU — базовый разумный минимум для совмещённых Hiddify/Xray/Caddy + Telegram bot/web. Заложить память под контейнеры, TLS, процессы Python и обновления, не запускать второй бот.
- NL-2: 2 GB RAM, 1 vCPU только для Xray + Hiddify child. Не запускать сайт, бота и платёжные службы. Возможны пики памяти при синхронизации и пересоздании конфигурации — нужен тест parent/child на фактической версии, особенно при старом Hiddify v0.8.4. Если тест не пройден, заменить тариф на Village+ или упростить функционал; не объявлять такой узел автоматическим резервом до проверки.
- **Отказоустойчивость ограничена:** RU-1 с единственной SQLCipher БД остаётся одиночной точкой отказа для новых платежей/подписок; уже выданные ключи могут продолжить работать. Для полноценного HA базы требуется отдельное реплицирование/failover, не включённое в бюджет. Все VPS у одного оператора, который остаётся общей точкой риска.
- Если денег хватает только на первые два VPS: RU-1 Farm+ (580 ₽) и NL-1 Village+ (1 040 ₽) = **1 620 ₽/мес.** Сначала миграция, затем резервные RU-2 и NL-2. Это временная схема без резервирования входа/выхода.
- Не экономить на подтверждённом внешнем backup и ключе расшифровки. Предыдущий DE-сервер под риском удаления в течение суток: до миграции проверить, что **оба** зашифрованных архива и SQLCipher/Hiddify базы скачаны, сверены и тест восстановления прошёл; не предполагать, что один файл покрывает AWG volumes.

**Источники:** официальная страница тарифов https://vpsvillage.ru/ ; API локаций https://api.vpsville.ru/docs/ .

VPSVILLE публично описывает использование VPS для проксирования и развёртывания VPN/OpenVPN. Это подтверждает техническую поддержку VPN-сценария. Но публичная страница сама по себе не является письменным разрешением на коммерческую перепродажу доступа третьим лицам. До заказа запросить support@vpsville.ru и сохранить ответ в проекте: разрешены ли коммерческий VPN с платными подписками, VLESS/REALITY, WireGuard, OpenVPN и пользовательская аутентификация.

## Обязательные вопросы VPSVILLE до оплаты

1. Разрешён ли коммерческий VPN-сервис с платными подписками сторонним пользователям (не только личный VPN), VLESS/REALITY, WireGuard и OpenVPN?
2. Можно ли заказать NL Village+ два раза с разными IPv4 и закрепить отдельные IP надолго?
3. Можно ли для RU-1 назначить IPv4 из AS204916, а RU-2 — из AS59504? Какие фактические ASN и аплинки у нидерландских адресов?
4. Каковы реальные ограничения по полосе на одну VPS, fair-use, объёму трафика, PPS и UDP? Заявленный порт 10 Gbit/s не считать гарантированной скоростью одного VPS без SLA.
5. Есть ли DDoS-защита IPv4/IPv6 в выбранном тарифе; включена ли она в цену? Каталоги тарифов расходятся по этому пункту.
6. Какова процедура abuse-жалоб, блокировки IP и приостановки VPS? Предупреждают ли до отключения, кроме экстренных случаев?
7. Есть ли автоматические snapshot/backup и сколько они стоят? Не считать их заменой собственной зашифрованной резервной копии.

Если поддержка не подтверждает коммерческое использование письменно, не размещать платный сервис до решения этого вопроса.

## Миграция без потери данных и простоя

### Фаза 0 — подготовка и свежая инвентаризация

1. Не отключать RUVDS и HOSTKEY. Не менять текущие DNS и клиентские подписки.
2. Получить с обоих серверов read-only снимок: версия Ubuntu, пакеты, systemd units, Docker/Compose, контейнеры, volumes, слушающие порты, firewall, WireGuard interfaces/peers, дисковая/RAM нагрузка, DNS-записи.
3. Сделать полный зашифрованный backup проекта: SQLCipher bot DB, Hiddify DB, конфигурации Caddy/Xray, compose/env/secrets, конфигурацию relay и firewall, WireGuard peer configs (закрытые ключи не печатать). Проверить SHA256 и восстановить копию в изолированном тесте.
4. Отдельно сохранить AWG volume/key, если владелец использует личный \`amnezia-awg2\`: текущий стандартный backup его не включает.
5. Проверить доступ к закрытому age-key вне серверов; не отправлять приватные ключи, токены и .env в GitHub/чат.

### Фаза 1 — заказ VPSVILLE

1. Заказать RU-1 Farm+, RU-2 Camp, NL-1 Village+, NL-2 Farm+ с Ubuntu 24.04 LTS.
2. Для NL выбрать только план с суффиксом «+»: API VPSVILLE указывает, что локация NL доступна на планах «Космос» с суффиксом «+».
3. До установки проверить в панели физическую локацию, выданный IPv4, gateway, обратную маршрутизацию и ASN. Сохранить ответы поддержки и счета.
4. Создать отдельные SSH ED25519 ключи/доступы для каждого сервера; отключить парольный SSH после проверки нового входа. Не использовать один приватный ключ, скопированный на все узлы.
5. Применить firewall и обновления ОС, затем проверить reboot и повторный доступ.

### Фаза 2 — сеть и RU база

1. Создать новые независимые WireGuard пары RU-1↔NL-1 и RU-2↔NL-2. Не переиспользовать private keys старых серверов. Закрытые ключи генерировать на соответствующем сервере.
2. На RU-1 перенести SQLCipher database gateway и рабочую БД по процедуре, основанной на \`scripts/db_cutover.sh\`; проверить поддержку gateway, token rotation и версию API.
3. База доступна только через WireGuard/private interface. Не публиковать DB gateway в интернет.
4. RU-2 — только stateless relay; никаких DB, telegram_id, платежей или пользовательских профилей.
5. Проверить health, replay/retry, backup endpoint и восстановление gateway при перезагрузке.

### Фаза 3 — NL-1 приложение и основной VPN

1. Сначала развернуть тот же проверенный release бота, web/PWA/TMA и compose, что на действующем DE. Не смешивать миграцию с обновлением Python/npm зависимостей.
2. Восстановить Hiddify DB и конфигурацию с действующего DE. Не обновлять Hiddify Manager в той же операции: в историческом снимке версия v0.8.4, а предыдущий черновик плана упоминал v14.x. Сначала выяснить реальную версию/ветку/образ и восстановить совместимую копию.
3. Настроить NL-1 как основной exit; RU-1 relay направляет входящие порты на NL-1.
4. Настроить бота на DB gateway RU-1 по WireGuard. Запустить ровно один polling-процесс бота.
5. Восстановить Caddy и web/PWA/TMA; проверить Telegram Login, домены, HTTPS, /healthz, /tma/, /oferta, оплату СБП QR, webhook/polling и активацию подписки.
6. Выполнить Hiddify client tests: создать тестового пользователя, импортировать подписку в Hiddify/v2rayNG/NekoBox, передать трафик, проверить внешний IP и usage.

### Фаза 4 — NL-2 и резервные маршруты

1. Не считать NL-2 полноценным резервом, пока не проверена синхронизация пользователей, сроков, квот, usage и revoke.
2. Проверить поддержку Multi-server/parent-child в фактически установленной версии Hiddify. Не предполагать, что старая версия v0.8.4 совместима с новой инструкцией multi-server. Если функция отсутствует — сначала испытать обновление/миграцию на тестовой копии; production не обновлять без rollback.
3. Если Multi-server совместим: NL-1 — parent, NL-2 — child; тестовый пользователь должен синхронизироваться, usage суммироваться, revoke действовать на обоих.
4. RU-2 relay направляет трафик к NL-2. Сначала --check для relay/firewall scripts, затем apply с автоматическим откатом и подтверждением из нового SSH-сеанса.
5. Отдельный subscription-only URL на NL-2 включать только после проверки реального ответа синхронизированного child. Старую подписку не менять до приёмки.
6. Если автоматическая синхронизация не подтверждена, NL-2 оставить standby и не публиковать его клиентам как автоматический failover.

### Фаза 5 — DNS, тестирование и вывод старых серверов

1. За 24 часа до cutover снизить TTL ключевых DNS-записей до 300 секунд (если текущий DNS-провайдер это позволяет).
2. Переключать по одной записи: app, panel, sub и входные VPN-домены. Сохранить старые IP/значения для отката.
3. Провести тесты минимум из трёх российских сетей: мобильные операторы и фиксированный интернет. Отдельно проверить TCP и UDP, VLESS/REALITY и Hysteria2, оплату, продление, revoke, обновление подписки.
4. Отключить по одному старому входу/выходу в тестовое окно и проверить резервный маршрут. Проверить reboot каждого нового VPS и восстановление контейнеров/туннелей.
5. Держать старые RUVDS/HOSTKEY включёнными минимум 7–14 дней после успешного переключения, пока нет ошибок платежей, выдачи подписок, БД и VPN.
6. Перед удалением старых VPS сделать финальную копию и проверить restore. Только затем отменить продление/удалить старые серверы. Не удалять старые диски до подтверждения возврата средств и наличия независимой копии.

## Критерии завершения

- Все сервисы проекта отвечают с новых VPSVILLE IP.
- В боте одна активная копия; платежи и активация работают.
- SQLCipher DB на RU-1; доступ к gateway только по WG; backup восстановлен.
- Hiddify users, ссылки, expiry, traffic quotas и revoke корректны.
- Вход через RU-1 и RU-2 и выход через NL-1 и NL-2 проверены из российских сетей.
- Доменная миграция завершена, TLS валиден, клиентские подписки обновляются.
- Не менее 7–14 дней без критических ошибок; только после этого старые VPS закрываются.

## Ограничение отказоустойчивости

Все четыре VPS находятся у одного оператора VPSVILLE. Даже при двух ASN, разных локациях и четырёх IP остаётся общий риск оператора/аккаунта/биллинга/магистрали. Эта схема снижает риск отказа отдельного VPS или IP, но не устраняет общепровайдерный отказ и не гарантирует обход блокировок по ASN. Для независимой аварийной копии хранить зашифрованные backup вне VPSVILLE.

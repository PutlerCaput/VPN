# Зашифрованные резервные копии в Cloudflare R2

`scripts/upload_r2_backup.py` переносит **готовый зашифрованный архив** в приватный
R2-бакет. Скрипт проверяет локальную SHA256, создаёт отдельный объект для каждого
запуска, затем полностью скачивает шифротекст потоком и сравнивает SHA256 и размер.
Только после совпадения создаёт локальный файл `*.verified.json` с адресом объекта.
При ошибке возвращает ненулевой код, исходный архив остаётся на месте. Непроверенный
объект может остаться в бакете; он не считается успешной резервной копией.

Это дополнение к `/root/backup-live-vpn.sh`, а не замена создания резервной копии.
Имя `.gpg`/`.enc` само по себе не доказывает шифрование. До загрузки должны пройти
проверка содержимого и восстановление баз, предусмотренные вашим backup-сценарием.
Совпадение шифротекста после загрузки не заменяет проверку расшифрования и восстановления.

## Однократная настройка

1. В Cloudflare → R2 создайте **приватный** бакет `cyberdefency-vpn-backups`.
   Публичный доступ `r2.dev` и публичный домен для него не включайте.
2. Создайте R2 S3-учётные данные с чтением и записью объектов **только этого бакета**.
   Обычный Cloudflare API-токен не заменяет R2 Access Key ID / Secret Access Key.
3. На сервере установите свежую AWS CLI v2 и выполните:

   ```bash
   aws --version
   aws configure --profile cyberdefency-r2
   ```

   Введите R2 Access Key ID и Secret Access Key только в терминале.
   Регион: `auto`, формат: `json`. CLI хранит ключ в файле, без шифрования:

   ```bash
   chmod 700 ~/.aws
   chmod 600 ~/.aws/credentials ~/.aws/config
   ```

## Загрузка проверенного архива

Запустите из каталога проекта на том сервере, где находится архив:

```bash
read -r -p 'Полный путь к проверенному .tar.gz.gpg архиву: ' ARCHIVE_PATH
python3 scripts/upload_r2_backup.py "$ARCHIVE_PATH" \
  --bucket cyberdefency-vpn-backups
```

Рядом должен существовать файл `имя-архива.sha256`, созданный при проверке резервной
копии. Он должен содержать ровно одну строку: SHA256, два пробела и имя архива или
его текущий абсолютный путь. Не создавайте новую контрольную сумму вместо
исправления ошибки проверки. Для другого пути к checksum передайте `--checksum`.

Успех: `VERIFIED_R2_RECEIPT=...verified.json`. Запись содержит `bucket`, `object_key`,
`sha256` и `size_bytes`, но не ключи. Сохраните её рядом с локальным архивом.
Объект записывается условным PUT (`If-None-Match: *`), поэтому существующий объект
не перезаписывается. Нужна AWS CLI v2 с поддержкой этого параметра. Максимальный
размер одного архива — 5 GiB; более крупные файлы отклоняются до загрузки.

Ключ восстановления `.recovery-key` храните отдельно от R2, например в защищённом
хранилище на ПК. Скрипт не загружает его и ничего не удаляет. Для восстановления
SQLCipher-БД также нужен её ключ из исходной защищённой конфигурации.

## Автоматизация и проверка восстановления

В существующем backup-задании запускайте uploader только после успешного завершения
создания и проверки архива, передавая точный путь нового файла. У задания должны быть
доступ к профилю `cyberdefency-r2` и уведомление владельцу при ненулевом коде выхода.
Автоматическое удаление локальных копий или lifecycle с удалением объектов пока не
включайте: сначала выполните восстановление скачанного из R2 архива в отдельной
среде. Не восстанавливайте пробную копию поверх работающей БД.

Из этой рабочей среды реальная загрузка не выполнялась: R2 S3-учётные данные и имя
созданного бакета не подтверждены. Локальные тесты проверяют в том числе повреждение
загрузки, усечение, таймауты, отказ записи и сохранность исходного файла.

# Закрыть панель Hiddify и отделить сайт от IP VPN

Подготовлено 17 ноября 2026 года, **не применено**. Всё выполняет владелец вручную на DE
(89.125.210.172). Зачем — `ARCHITECTURE.md`, раздел 5; `ANTI_CENSORSHIP_AUDIT.md`, п. 4.3
и 5.3.

## 1. Что открыто сейчас (ничего не меняет)

```bash
bash /root/vpn-src/scripts/de_lockdown.sh
```

Печатает состояние ufw, слушающие сокеты, порты контейнеров и точный список правил, которые
поставит `--apply`. Сверить:

- все порты из «listening», которые должны быть доступны клиентам, есть в плане
  (по умолчанию TCP 80, 443, 8443, 2443 и SSH; UDP 36099, 39051, 44877; весь UDP с RU;
  всё, что приходит в `wg-vpn`). Если Hiddify слушает ещё что-то нужное (например 2080),
  добавить: `ALLOW_TCP="80 443 8443 2443 2080" bash de_lockdown.sh`;
- **порты контейнеров Docker ufw не фильтрует** (Docker ставит свои правила iptables).
  Если панель или другой сервис опубликован через `-p`, закрывать его нужно в compose
  (`127.0.0.1:PORT:PORT`), а не ufw;
- куда ходит бот за API панели: `docker exec node-rental-bot-1 printenv HIDDIFY_URL`.
  Если это `panel.…:8443`, шаг 3 обязателен в
  варианте с allowlist для Docker-сети, иначе бот потеряет панель.

## 2. ufw: только нужные порты

```bash
bash /root/vpn-src/scripts/de_lockdown.sh --apply
```

Порядок внутри: копия `/etc/ufw` в `/root/de-lockdown/ufw-<время>`; таймер отката на
10 минут (`systemd-run`) **до** любых изменений; разрешающие правила (SSH первым); затем
`default allow routed` (AmneziaWG маршрутизирует клиентов через DE, DROP их бы отрезал),
`default deny incoming`; `ufw enable`. Текущая SSH-сессия не рвётся.

В течение 10 минут **из нового окна** войти по SSH и проверить:

```bash
bash /root/vpn-src/scripts/update_bot.sh --doctor   # 0 problems, «Hiddify Manager panel answers»
wg show wg-vpn latest-handshakes      # туннель с RU жив
ss -lnu | grep -E '36099|39051|44877' # Hysteria2 и AmneziaWG слушают
```

С телефона: Hysteria2, gRPC Reality через RU и AmneziaWG подключаются. Если всё хорошо:

```bash
bash /root/vpn-src/scripts/de_lockdown.sh --confirm
```

Откат в любой момент (и автоматически, если не было `--confirm`):

```bash
bash /root/vpn-src/scripts/de_lockdown.sh --revert
```

Возвращает `/etc/ufw` из копии; если ufw до этого был выключен — выключает его.

## 3. Панель только для владельца

Панель и подписка живут на одном порту Caddy (8443) под разными именами, поэтому ufw их не
различает: ограничение ставится на сайт панели в Caddy. Найти блок сайта панели:

```bash
grep -rn 'panel\.' /opt/hiddify-manager/Caddyfile /etc/caddy 2>/dev/null
```

Внутри блока `panel.cyberdefency.com:8443 { ... }` обернуть существующие директивы
(копию файла сделать заранее: `cp -a <файл> <файл>.pre-lockdown`):

```caddy
	@owner remote_ip 127.0.0.1/8 172.16.0.0/12 10.205.0.0/24 {$PANEL_ADMIN_IPS}
	handle @owner {
		# ... прежние директивы сайта панели без изменений ...
	}
	handle {
		abort
	}
```

- `127.0.0.1/8` — доступ владельца через SSH-туннель;
- `172.16.0.0/12` — бот в Docker (запрос бота на свой же адрес приходит с адреса
  контейнера); проверить после перезагрузки Caddy: `update_bot.sh --doctor` → «Hiddify Manager panel
  answers»;
- `PANEL_ADMIN_IPS` — необязательно, постоянный IP владельца.

Проверить и применить: `caddy validate --config <файл>` → `systemctl reload caddy` (или
`docker exec <caddy> caddy reload ...`, как у вас запущен). Если Hiddify перегенерирует
свой Caddyfile при «Применить», правку нужно повторить после каждого применения настроек
панели (как с ночным автообновлением) — проверять после изменений в панели.

Доступ владельца:

```bash
ssh -L 8443:127.0.0.1:8443 root@89.125.210.172
# в /etc/hosts компьютера: 127.0.0.1 panel.cyberdefency.com
# браузер: https://panel.cyberdefency.com:8443/<admin proxy path>/
```

Откат: вернуть `<файл>.pre-lockdown` и перезагрузить Caddy.

Подписка `sub.cyberdefency.com:8443` остаётся открытой: ею пользуются приложения. Когда
включено шардирование и все перешли на новую ссылку (`ARCHITECTURE.md`, раздел 4), прямую
подписку тоже закрыть так же (`@owner` с адресами Docker-сети: бот скачивает её сам).

## 4. Сайт отдельно от IP VPN

Сейчас `app.cyberdefency.com` указывает на 89.125.210.172 — тот же адрес, что выход VPN.
Блокировка домена сайта по IP задевает VPN, а адрес VPN виден любому, кто открыл сайт.

Варианты (по возрастанию изоляции):

1. **CDN (Cloudflare, оранжевое облако)** для `app.…` — `docs/CLOUDFLARE_SETUP.md`. На DE
   порт 443 для сайта открыть только адресам Cloudflare. Минус: доступность Cloudflare из
   РФ нестабильна (замедления с 2024 года), Mini App и оплата должны работать — проверить с
   мобильного без VPN. `sub.…` оставить «DNS only» до перехода на шардированную ссылку, затем
   перенести вместе с сайтом.
2. **Отдельный небольшой сервер** (лучше — российский хостер, не тот, где RU-1) с Caddy:
   статика PWA/TMA и `reverse_proxy` на бота по туннелю (`deploy/web/frontdoor.caddy`,
   `docs/WEB_DEPLOYMENT.md`). Сайт и подписка тогда вообще не на адресе VPN.
3. Перенести бота с сайтом на отдельный сервер целиком; DE остаётся только выходом VPN.

Откат для 1: снять проксирование в Cloudflare (серое облако). Для 2–3: вернуть A-запись
`app.…` на DE; конфигурация Caddy на DE при этом не удаляется.

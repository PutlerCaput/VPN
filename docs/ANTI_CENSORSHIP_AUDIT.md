Актуально на 14 ноября 2026 года. Основано на выводах владельца с серверов и на замерах пробника.
Что про ТСПУ взято из открытых сообщений сообщества, а не из проверки, помечено «по сообщениям».
Любую меру проверяют замерами (`PROBE_RU_MOBILE.md`), а не верой.

## 2. Что уязвимо (по убыванию важности)

1. **Сайт, панель и VPN на одном IP DE.** `app.…` (Caddy на 443) и панель Hiddify Manager (`panel.…:8443`)
   живут на том же адресе, что и вход VPN. Цензор получает адрес VPN из DNS сайта без всякого DPI,
   а панель Hiddify Manager на 8443 опознаётся сканером по странице входа. Это главная уязвимость: не
   нужно распознавать трафик, адрес уже назван.
2. **Один вид трафика.** Все VLESS-клиенты идут одним рисунком (TCP + REALITY + Vision). Одно правило
   закрывает всех. AmneziaWG — второй вид, но UDP у мобильных операторов режут чаще.
3. **Маскировка `www.apple.com`.** Одна из самых частых в инструкциях. Несовпадение «SNI Apple —
   адрес немецкого хостинга» видно пассивно, без зондирования. Активному зондированию REALITY
   противостоит хорошо (сканер получает настоящий сертификат Apple), но пассивная эвристика по
   паре SNI/ASN её не замечает.
4. **Нестандартные порты 2096/2097.** TLS на нестандартном порту — дополнительный признак. Через
   RU-вход клиент идёт на 443, это лучше.
5. **Зарубежный адрес у мобильных операторов.** По сообщениям сообщества, у части операторов
   соединения TCP к зарубежным адресам хостингов «замерзают» после первых ~16 КБ. RU-вход обходит
   это: клиент соединяется с российским адресом. Прямой DE-вход — запасной путь на случай, если
   заблокируют RU.
6. **Лишняя запись Shadowsocks** в таблице адресов Hiddify Manager (`{SERVER_IP}`, входа такого в Xray нет):
   мусор, который может попасть в подписку.

## 3. Протоколы

| Протокол | За | Против | Решение |
|---|---|---|---|
| VLESS + REALITY + Vision (TCP) | Нет своего сертификата; на зондирование отвечает чужой сайт; Vision убирает признак «TLS в TLS» | Один рисунок; пара SNI/ASN | Оставить основным |
| VLESS + REALITY + gRPC | Другой рисунок (HTTP/2-кадры); тот же ключ | Без Vision: «TLS в TLS» заметнее; чуть больше нагрузка на CPU | Включить как второй (готово, `vless_transport.sh`) |
| VLESS + REALITY + XHTTP | Рекомендуемый Xray транспорт с 2025 года; гибкое разбиение запросов | Hiddify Manager v0.8.4 не умеет выдавать его в подписке | После обновления панели (п. 7) |
| AmneziaWG | Быстрый, хорош на домашних сетях; параметры Jc/Jmin/Jmax/S/H ломают сигнатуру WireGuard | UDP; userspace-реализация медленнее модуля ядра | Оставить |
| Hysteria2 (QUIC) | Лучший на сетях с потерями | UDP/QUIC к зарубежным адресам в РФ режут часто; нужен отдельный сервер (sing-box) | Не сейчас: замеры UDP сначала |
| Trojan, Shadowsocks | — | Ничего не добавляют к REALITY; SS легко распознаётся | Не использовать; лишнюю запись SS убрать |

## 4. Маскировка

### 4.1. Выбор имени для REALITY

Требования: TLS 1.3, HTTP/2, без редиректа на другой домен, **по возможности сайт в той же сети
(ASN), что и сервер**: тогда «SNI сайта X на адресе хостинга X» не выглядит странно. Инструмент
XTLS для поиска таких соседей:

```bash
# DE. Ищет сайты с TLS 1.3 + h2 в сети сервера. Только для выбора имени, ничего не меняет.
cd /root && curl -sLO https://github.com/XTLS/RealiTLScanner/releases/latest/download/RealiTLScanner-linux-64
chmod +x RealiTLScanner-linux-64
./RealiTLScanner-linux-64 -addr DE_SERVER_IP -port 443 -thread 20 -timeout 5 -out scan.csv
```

Кандидатов из `scan.csv` проверить нашей проверкой (TLS 1.3 + HTTP/2 с этого сервера):

```bash
bash /root/vpn-src/scripts/vless_transport.sh --check ИМЯ
```

Компромисс: сосед по сети малоизвестен, и если его сайт пропадёт, маскировку придётся менять.
Крупные (`dl.google.com`) стабильнее, но пара SNI/ASN у них не совпадает.

### 4.2. Отпечаток клиента (uTLS)

В адресах подписки задать `fingerprint: chrome`: клиентский TLS тогда неотличим от браузера Chrome.
В Hiddify Manager это поле адреса (Hosts → Fingerprint). Проверка, что задано:
`docker exec -i node-rental-bot-1 python3 - < /root/vpn-src/scripts/vpn_entries.py` (поле
`fingerprint=`).

### 4.3. Защита от сканеров

```bash
# DE. Панель Hiddify Manager — только с адресов владельца/через SSH-туннель, не всему интернету.
ufw delete allow 8443/tcp
ufw allow from RU_SERVER_IP to any port 8443 proto tcp comment 'panel via RU only'
# Доступ владельца к панели: ssh -L 8443:127.0.0.1:8443 de, затем https://localhost:8443
```

Компромисс: бот обращается к API Hiddify Manager по `127.0.0.1:8000` (не через 8443) — его это не
затрагивает; проверить до применения (`--doctor`: «Hiddify Manager panel answers»).

Сайт `app.…` с IP VPN — перенести (п. 5.3).

## 5. Архитектура

### 5.1. Посредник в РФ

Нужен: обходит ограничения на зарубежные адреса. Минусы: хостер видит метаданные (не содержимое:
REALITY заканчивается в DE), может быть вынужден отключить. Решение: **второй посредник у другого
российского хостера** (другая сеть), с тем же DNAT. Тогда блокировка одного хостера не отключает
никого.

```bash
# Новый RU-сервер: те же пробросы, что на нынешнем (ru_firewall.sh держит INPUT; DNAT — так):
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A PREROUTING -p tcp --dport 443 -j DNAT --to-destination DE_SERVER_IP:2096
iptables -t nat -A POSTROUTING -d DE_SERVER_IP -p tcp --dport 2096 -j MASQUERADE
# На DE разрешить 2096 и с нового адреса; в подписку — его адрес:
docker exec -i node-rental-bot-1 python3 - --add NEW_RU_IP:443 < /root/vpn-src/scripts/vpn_entries.py
```

Посредник в соседней стране (Казахстан, Армения) — по сообщениям, адреса этих стран режут реже,
чем европейские хостинги, но и там бывают ограничения. Имеет смысл, если замеры покажут, что
прямой DE-вход у операторов не работает, а RU — под угрозой.

### 5.2. Раздельная маршрутизация

Уже работает: российские сайты напрямую (`ru_direct.sh`). Плюсы: банки и госуслуги не видят
зарубежный IP; меньше трафика через VPN. Поддержать актуальность: геобазы обновляются по
расписанию (`deploy/xray/update_geodata.sh`), правила в подписке — `ru_direct.sh`.

### 5.3. Разнести сайт и VPN

Сайт и Mini App — на отдельный дешёвый сервер или за CDN; DE остаётся только VPN. Тогда домен
сайта не выдаёт адрес VPN. Компромисс: ещё один сервер; бот и база остаются как есть.

## 6. Отказоустойчивость

- **Несколько адресов в подписке** (сделано: RU:443, DE:2096; дальше gRPC и второй RU). Клиент с
  автовыбором переключается сам: Hiddify/sing-box — группа `urltest`, v2rayNG — «Проверить все» и
  выбрать лучший (вручную). Рекомендовать клиентам Hiddify для автопереключения.
- **Смена адреса при блокировке**: у хостеров есть дополнительные IP; новый адрес добавляется
  `vpn_entries.py --add`, старый убирается `--remove`, клиенты получают изменения с подпиской.
  Автоматически — после автопилота (решение по замерам, откат, уведомление).
- **Домены входа**: адрес входа именем (`e1.домен`) с коротким TTL позволяет менять IP без
  обновления подписки. Компромисс: домен сам может попасть в реестр — держать отдельный от сайта.
- **CDN (Cloudflare)**: прячет IP, но с REALITY не работает (нужен свой сертификат и WS/XHTTP через
  CDN), а Cloudflare в РФ режут (наш же опыт: туннель Cloudflare с RU рвался каждые ~3 минуты,
  `NETWORK_RESILIENCE.md`). Только как последний запасной вход.

## 7. Обновление панели

Hiddify Manager v0.8.4 не выдаёт XHTTP. Варианты: ветка разработки Hiddify Manager или Remnawave/Marzneshin. Это
смена формата базы и подписок — отдельный проект с переносом пользователей и полной проверкой на
копии. Делать после автопилота, не раньше.

## 8. Производительность

```bash
# DE и RU. BBR + fq: меньше задержка при потерях (мобильные сети).
cat >/etc/sysctl.d/90-vpn-tuning.conf <<'EOF'
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216
net.ipv4.tcp_mtu_probing = 1
net.ipv4.tcp_fastopen = 3
EOF
sysctl --system | tail -3
sysctl net.ipv4.tcp_congestion_control   # должно быть bbr
```

На DE и на RU то же самое делает `bash scripts/net_tuning.sh`: пишет этот файл,
загружает модуль `tcp_bbr` и записывает его в `/etc/modules-load.d/bbr.conf`,
выполняет `sysctl --system` и ставит корневую qdisc `fq` на интерфейс маршрута
по умолчанию (`tc qdisc replace`). Повторный запуск безопасен.
`bash scripts/net_tuning.sh --check` только печатает текущие значения.

```bash
# RU. Посредник меняет путь: MSS по MTU, чтобы не было «зависаний» больших пакетов.
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

- MTU AmneziaWG у клиента 1280: безопасно для мобильных сетей, на домашних можно 1380–1420.
- Нагрузка: REALITY + Vision почти не нагружает CPU (TLS проходит без перешифрования); gRPC — да,
  на слабом VPS при сотнях клиентов это заметно. amneziawg-go в userspace медленнее модуля ядра в
  разы; при упоре в CPU — ставить модуль ядра AmneziaWG (DKMS).

# Обслуживание сервера: обновление, очистка, лимит трафика

Редакция от 8 ноября 2026. Команды выполняются на DE-сервере из папки
`/root/vpn-src`. Сначала всегда отчёт без изменений, потом изменение.

## Команды с телефона

Нужен вход на сервер по SSH или веб-консоль хостинга.

**Веб-консоль хостинга (VNC).** Панель хостинга в браузере телефона, раздел
«Консоль». Идёт мимо SSH, ключи не нужны. Подходит, когда SSH недоступен или
нужно сверить отпечаток ключа сервера. Печатать в ней неудобно.

**SSH-клиент.** Termius (iPhone и Android) или Termux (Android; пошагово ниже).
Правила одни для любого клиента:
- Свой ключ на каждое устройство: ключ с компьютера на телефон не копируйте.
- При первом подключении клиент показывает отпечаток ключа сервера. Принимайте
  его, только если он совпал с одним из отпечатков, которые даёт консоль
  хостинга (в Termius отпечаток может быть в виде MD5: тогда `-E md5`):

  ```bash
  for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$f"; done
  ```

- Потеряли телефон: удалите его строку из `/root/.ssh/authorized_keys`.

### Termux (Android) пошагово

1. **Установка.** Из [F-Droid](https://f-droid.org/packages/com.termux/) или со
   страницы [GitHub termux/termux-app](https://github.com/termux/termux-app/releases),
   файл `arm64-v8a` для современного телефона. Не из других источников и не из
   копий на GitHub. Источники не смешивайте: если Termux уже стоит из другого
   места, сначала удалите его.
2. **Первый запуск.** Если спросит про файлы настроек, нажмите Enter.

   ```bash
   pkg update -y && pkg upgrade -y
   pkg install -y openssh
   ```

3. **Ключ телефона.** Придумайте фразу-пароль для ключа и запомните её: с пустой
   фразой ключ никак не защищён.

   ```bash
   mkdir -p ~/.ssh && chmod 700 ~/.ssh
   ssh-keygen -t ed25519 -C phone -f ~/.ssh/id_ed25519
   ```

   Команда спросит только фразу, два раза. При вводе она на экране не
   показывается, это нормально. Следующие команды вводите после того, как
   `ssh-keygen` закончит, иначе они попадут в ответы. Проверка: `ls ~/.ssh`
   показывает файлы `id_ed25519` и `id_ed25519.pub`. Если их нет, повторите шаг.
   Файл без `.pub` — закрытый ключ: никому не показывайте и не пересылайте его.
   Если ключ всё же создался под другим именем (в вопросе про путь ввели своё
   слово, например `Dowloads`), переложите файлы, фраза при этом сохраняется:
   `mv ~/Dowloads ~/.ssh/id_ed25519 && mv ~/Dowloads.pub ~/.ssh/id_ed25519.pub`.
4. **Короткое имя сервера.** `ServerAlive…` не даёт мобильной сети молча
   «заморозить» соединение.

   ```bash
   cat > ~/.ssh/config <<'EOF'
   Host de
       HostName 89.125.210.172
       User root
       ServerAliveInterval 30
       ServerAliveCountMax 4
   EOF
   chmod 600 ~/.ssh/config
   ```

5. **Первое подключение.** Выполните `ssh de`. На вопрос
   `Are you sure you want to continue connecting` сверьте отпечаток из вопроса
   (тип ED25519 или RSA указан рядом) с выводом консоли хостинга. Совпал:
   `yes`. Не совпал: Ctrl+C и пароль не вводите.
6. **Ключ на сервер.** Обычно root пускают на сервер только по ключу, а пароль
   отвергают, даже верный. Тогда `ssh` отвечает
   `Permission denied (publickey,password)`: ключа телефона на сервере ещё нет, и
   пароль не поможет. Пароль подбирать не нужно. Добавьте ключ через консоль
   хостинга: она входит прямо на машину, и пароль root там работает.
   1. В Termux: `cat ~/.ssh/id_ed25519.pub`. Это открытый ключ, он не секрет.
      Скопируйте строку целиком, долгим нажатием на текст. Чтобы вставить её с
      компьютера, отправьте её себе в Telegram («Избранное»). Отпечаток ключа:
      `ssh-keygen -lf ~/.ssh/id_ed25519.pub`.
   2. Консоль хостинга: логин `root` и его пароль. Если пароля нет, сбросьте его в
      панели хостинга. Не нажимайте «Переустановить ОС»: она стирает диск
      вместе с базами бота и Marzban.
   3. В консоли. Вставка с телефона в консоль хостинга часто не работает:
      откройте консоль в браузере на компьютере и вставьте строку там либо
      введите её вручную.

      ```bash
      mkdir -p /root/.ssh && chmod 700 /root/.ssh
      printf '\n%s\n' 'ВСТАВЬТЕ_СТРОКУ' >> /root/.ssh/authorized_keys
      chmod 600 /root/.ssh/authorized_keys
      ssh-keygen -lf /root/.ssh/authorized_keys
      ```

      Последняя команда показывает отпечатки всех ключей в файле. Отпечаток
      телефона должен совпасть с тем, что показал Termux: так видно, что строка
      вставлена без опечаток. Перевод строки в начале (`\n`) обязателен: если
      у последней строки файла его нет (так бывает с ключом, который хостинг
      положил сам), новый ключ приклеивается к ней, и `sshd` его не видит. В
      отчёте `ssh_hardening.sh` такая строка помечена предупреждением.

   Знак `>>` дописывает строку и не трогает прежние ключи (ключ с компьютера
   останется). Именно `>>`, не `>`: одна стрелка стёрла бы остальные ключи.
   Если root всё же принимает пароль, то же делает одна команда из Termux:

   ```bash
   { echo; cat ~/.ssh/id_ed25519.pub; } | ssh de 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
   ```

   Если вы вводили пароль root до сверки отпечатка ключа сервера, смените его в
   консоли хостинга командой `passwd`.
7. **Проверка.** `ssh de` теперь спрашивает только фразу ключа, пароль сервера
   не нужен. Дальше всегда так:

   ```bash
   ssh de
   tmux new -s update        # или, если уже есть: tmux attach -t update
   ```

8. **Удобства.** Ctrl: кнопка CTRL в верхнем ряду клавиш или кнопка «Громкость −».
   Вставка: долгое нажатие на экран, пункт Paste. Чтобы Android не усыплял
   Termux: в шторке уведомлений у Termux нажмите «Acquire wakelock» и выключите
   для него оптимизацию батареи. Само обновление при этом защищено tmux на
   сервере. Обновлять сам Termux: `pkg upgrade`.

**Долгие команды запускайте в tmux.** На мобильной сети связь обрывается, и
обычная команда обрывается вместе с ней. `server_update.sh --apply` по SSH без
tmux или screen сам откажется запускаться и покажет, что делать.

```bash
tmux new -s update                # новая сессия
cd /root/vpn-src && bash scripts/server_update.sh --apply
# связь оборвалась: войдите снова и откройте ту же сессию
tmux attach -t update
```

Выйти из tmux, не прерывая команду: Ctrl+B, затем D. Если tmux нет:
`apt-get install -y tmux`.

Секреты не вставляйте в чат и не печатайте в обычной команде: ключи и токены
`update_bot.sh --set-secret` запрашивает скрытым вводом. Команды выполняйте
только из этого репозитория и из ответов, которые вы запрашивали сами.

## SSH пишет «HOST IDENTIFICATION HAS CHANGED» или «Permission denied»

Сначала откройте консоль хостинга. Если там `rescue login` или
`Debian GNU/Linux … rescue`, сервер загружен в **режим восстановления**.
Отвечает временная система хостинга со своими ключами и паролем, поэтому SSH
жалуется на смену ключа и не принимает ваши пароль и ключи. Ваши бот, сайт и VPN
при этом не работают. Отключите режим восстановления в панели хостинга и
перезагрузите сервер: прежний ключ сервера вернётся, и предупреждение
исчезнет. Строку с ключом в поле `login` вводить не нужно: это поле имени.

Если консоль показывает приглашение вашей системы (`cheburnetnash login:`),
а ключ всё равно отличается, пароль не вводите. Сверьте отпечатки из
предупреждения клиента с теми, что даёт консоль хостинга:
`for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$f"; done`.

## Вход на сервер только по ключу

Пароль к SSH подбирают боты со всего интернета, ключ подобрать нельзя.
`scripts/ssh_hardening.sh` выключает вход по паролю и оставляет только ключи. Без
`--apply` он ничего не меняет, а применённое снимает сам, если вы не подтвердили,
что вход по ключу из нового окна работает. Порт, файрвол (от них зависит VPN) и
ключи самого сервера он не трогает: после смены ключа сервера каждый клиент
показывает «HOST IDENTIFICATION HAS CHANGED». Fail2ban не ставит: когда пароли
выключены, подбор ничего не даёт, а лишний процесс на маленьком сервере и риск
заблокировать самого себя не нужны.

1. **Отчёт**, ничего не меняет:

   ```bash
   cd /root/vpn-src && bash scripts/ssh_hardening.sh
   ```

   Что смотреть:
   - **Ключи.** Каждый ключ из `authorized_keys` пронумерован (`#1`, `#2`…), с
     подписью (комментарием), отпечатком и числом входов за 14 дней. Свой ключ
     опознают по отпечатку: на телефоне `ssh-keygen -lf ~/.ssh/id_ed25519.pub`
     (Termux), на компьютере в PowerShell
     `ssh-keygen -lf $env:USERPROFILE\.ssh\id_ed25519.pub`. Ключ, которого вы не
     узнаёте, чужой, пока не доказано обратное.
   - **Входы.** Для каждого входа по ключу показаны адрес, номер ключа и время
     последнего входа. Незнакомый адрес откройте в браузере как `ipinfo.io/<адрес>`:
     там видно владельца (мобильный оператор, Cloudflare WARP, ваш хостинг). Адрес
     самого сервера в списке означает вход, пока на устройстве включён VPN, который
     выходит через этот сервер; адрес RU-сервера значит вход с него. Вход по ключу,
     которого нет в списке, означает, что ключ уже удалили или он взят из другого файла.
   - **Входы по паролю** перестанут работать. Если это ваш компьютер, до `--apply`
     убедитесь, что его ключ в списке; если программа или RU-сервер, заведите им ключ.
   - Строки `set:` показывают, что изменится; `keys: ready` и `log: ready` значат,
     что условия выполнены.

   **Чужой ключ** удаляется одной командой по первым 6 и более символам
   отпечатка (после `SHA256:`), копия прежнего файла остаётся рядом:

   ```bash
   bash scripts/ssh_hardening.sh --remove-key ПЕРВЫЕ_СИМВОЛЫ
   ```

   Последний ключ скрипт не удалит. Ключ, которым вы входите сейчас, не удаляйте:
   новый вход этим устройством перестанет работать, пока вы не вернёте строку из
   копии через консоль хостинга. Если чужой ключ был в списке, считайте, что в
   сервер уже входили: смените пароль root (`passwd` в консоли хостинга) и
   напишите мне, что показал отчёт.
2. **Применить** (в tmux, из сеанса Termux по ключу, не из консоли хостинга):

   ```bash
   bash scripts/ssh_hardening.sh --apply
   ```

   Ответ `SSH_HARDENING_APPLIED`: для новых подключений пароль выключен. Это окно
   **не закрывайте**.
3. **Проверить новым входом.** В Termux откройте новое окно (проведите от левого
   края экрана, кнопка NEW SESSION) и войдите, нарочно запретив пароль:

   ```bash
   ssh -o PasswordAuthentication=no de
   ```

   Пустило: в этом новом окне выполните
   `cd /root/vpn-src && bash scripts/ssh_hardening.sh --confirm`, ответ
   `SSH_HARDENING_OK`. Не пустило или сомневаетесь: ничего не делайте, через 10
   минут прежние настройки вернутся сами. Вернуть сразу можно в первом окне:
   `bash scripts/ssh_hardening.sh --revert`.
4. **Потом.** `bash scripts/update_bot.sh --doctor` показывает строку
   `OK ssh: password login is off, keys only`. Если настройки откатились (не
   подтвердили), там будет `WARN`: повторите с шага 2.

Скрипт сам отказывается (`SSH_HARDENING_STOPPED`), если нет ключа в
`/root/.ssh/authorized_keys` (добавьте его, шаг 6 руководства по Termux) или в журнале
нет входа по ключу за 14 дней (войдите с телефона по ключу и запустите из этого
сеанса). Если он пишет, что настройки «not in force», какой-то файл в `/etc/ssh`
читается раньше нашего; сообщение называет команду поиска, и ничего не
изменено. Запасной вход при любой беде: консоль хостинга, она идёт мимо SSH.

## Обновление сервера

Одна команда обновляет пакеты системы (Docker тоже), базовые образы, бота и
сайт и проверяет базы данных.

```bash
cd /root/vpn-src
bash scripts/server_update.sh            # отчёт: меняет только списки пакетов
tmux new -s update                       # по SSH: обновление запускают в tmux
bash scripts/server_update.sh --apply    # обновление; в конце SERVER_UPDATE_OK
```

Запускайте раз в месяц в тихий час. Что делает `--apply` (при ошибке
останавливается на этом шаге):

0. **Место на диске.** Нужно около 5 ГБ свободных на `/`: пакеты, образы и две
   сборки. Если свободно меньше, скрипт сначала чистит сервер
   (`server_cleanup.sh --apply`). Если после очистки меньше 3 ГБ, он не
   начинает обновление и пишет, сколько места осталось. Отчёт без `--apply` тоже
   показывает свободное место, объём памяти и swap.
1. **Копии.** База Marzban копируется без остановки и проверяется на
   целостность. Копируются также настройки Marzban (`/opt/marzban`,
   `xray_config.json`), `.env` бота и `secrets`. Всё складывается в
   `/root/server-backups`, доступ только у root, хранятся три последние копии.
2. **Пакеты системы.** Пакеты обновляются, ни один не удаляется, изменённые
   вами файлы настроек сохраняются. Прежние версии пакетов Docker записываются,
   а в выводе есть готовая команда, чтобы откатить версию. Если обновляется
   Docker, контейнеры перезапускаются, и связь у клиентов прерывается примерно
   на минуту. Скрипт ждёт, пока снова заработают все контейнеры, которые
   работали до обновления.
3. **Бот и сайт.** Сначала скачиваются свежие базовые образы с исправлениями
   безопасности, кроме образа-сборщика Caddy: его обновление пересобрало бы сам
   Caddy, а это около гигабайта памяти и диска на небольшом сервере. Затем бот
   и сайт пересобираются через `update_bot.sh` и
   `update_web.sh`. Каждый из них сохраняет прежний образ и сам возвращается на
   него, если новый не прошёл проверку.
4. **Очистка и проверка.** Запускается `server_cleanup.sh --apply` (см. ниже).
   `--doctor` выполняется до и после обновления.

Не трогается: версия и настройки Marzban, Xray, его правила и geo-файлы,
файрвол, SSH. Новое ядро начинает работать только после перезагрузки. Если она
нужна, отчёт пишет `REBOOT NEEDED`: перезагрузите сервер командой `reboot` в
тихий час, контейнеры поднимутся сами.

### Если что-то пошло не так

- `SERVER_UPDATE_STOPPED: …` — шаг не удался. Всё до него сделано, дальше
  ничего не начато. Пришлите вывод.
- `SERVER_UPDATE_DONE_WITH_NEW_PROBLEMS` — обновление прошло, но `--doctor`
  нашёл новые проблемы. Строки `FAIL` в выводе говорят, что не так. Прежние
  образы бота и сайта сохранены: `docker images node-rental-bot` и
  `docker images node-rental-web`.
- Docker после обновления работает не так: выполните команду из строки
  `downgrade if ever needed`.
- База Marzban повреждена: остановите Marzban (`marzban down`), замените
  `/var/lib/marzban/db.sqlite3` последней копией из
  `/root/server-backups/marzban-db-*.sqlite3` и запустите (`marzban up`).

## Очистка

Вручную, раз в месяц и с присмотром, — ниже. Безопасную часть можно отдать
таймеру: раздел «Автоочистка раз в неделю».

```bash
bash scripts/server_cleanup.sh            # отчёт: ничего не удаляет
bash scripts/server_cleanup.sh --apply    # удаляет то, что в отчёте помечено would remove
```

Удаляется само:
- старые образы бота и сайта (кроме двух последних образов для отката) и
  неиспользуемые слои. Кэш сборки сокращается до 2 ГБ: остаются слои последних
  сборок, поэтому следующая сборка не становится медленной;
- другие версии образов работающих сервисов, которые не использует ни один
  контейнер (при необходимости они скачаются снова);
- старые копии баз и `.env` после обновлений, старые ключи;
- журнал системы старше 14 дней, кэш apt;
- старые ядра — только те, что выбрал бы сам apt; работающее ядро не трогается;
- логи контейнеров больше 200 МБ: файл лога очищается, контейнер продолжает
  работать;
- технические строки базы бота (перед этим делается проверенная копия).

Только показывается, решение за вами (рядом с каждым пунктом есть команда):
- образы, которые не использует ни один контейнер;
- остановленные контейнеры;
- тома Docker без контейнера (данные в них пропадут при удалении);
- большие архивы и логи в `/root`, которые не менялись две недели.

### Автоочистка раз в неделю

Включается один раз. Дальше сервер чистится сам, а проекту это не вредит: таймер
делает только безопасную часть очистки.

```bash
cd /root/vpn-src
bash scripts/server_cleanup.sh --auto --dry-run   # что сделал бы прямо сейчас, ничего не удаляет
bash scripts/install_cleanup.sh                   # включить и сразу сделать первый проход
```

Срабатывает по воскресеньям около 04:30 UTC, после ночной копии. Тихий режим
(сообщение только при проблеме): `bash scripts/install_cleanup.sh --quiet`.
Выключить: `bash scripts/install_cleanup.sh --remove`.

**Что удаляет.** Только то, что обновление уже заменило, и ничего моложе 7 дней:
- старые образы для отката и временные образы обновлений (два последних образа
  для отката каждого сервиса и всё, что использует контейнер, остаются);
- неиспользуемые слои старше 7 дней и кэш сборки выше 2 ГБ, не нужный последние
  трое суток;
- копии базы и `.env` после обновлений: две последние и всё моложе 7 дней остаются;
- журнал системы старше 14 дней, кэш apt, логи контейнеров больше 200 МБ.

**Чего не делает никогда.** Не трогает старые ядра, базу бота, другие версии
образов (к прежней версии Marzban вы можете захотеть вернуться), старые ключи в
`secrets/`, папки `/root/vpn-update` и `/root/vpn-new`, остановленные контейнеры и
тома Docker. Это остаётся ручной очистке (`--apply`) и ежемесячному
`server_update.sh`.

**Защиты.**
- Ничего не делает, пока идёт обновление, копия, восстановление, смена настроек
  SSH, обновление пакетов или другая очистка. Тогда пишет `SKIPPED` и пробует через
  неделю.
- Ничего не делает, если бот остановлен или какой-то контейнер нездоров,
  перезапускается или ещё стартует: когда что-то не так, образы для отката
  нужнее места.
- Образы удаляются без `-f`: образ, который использует контейнер, Docker не отдаст.
- После очистки проверяет, что работают те же контейнеры и все здоровы. Если
  нет, пишет вам в Telegram и завершается с ошибкой.

**Что приходит в Telegram.** Раз в неделю одна строка: сколько освобождено и
сколько свободно. Если свободно меньше 3 ГБ, предупреждение. Если появились
остановленные контейнеры, тома или образы без контейнера, строка скажет, сколько
их (один раз, пока число не вырастет); удалять их или нет, решаете вы.

**Проверка.** `bash scripts/update_bot.sh --doctor` показывает строку
`weekly cleanup`: когда была последняя очистка и сколько освободила. Предупреждение
появится, если таймер выключен, очистка не завершалась 10 дней или упала. Вывод
последнего запуска: `journalctl -u node-cleanup.service -n 60 --no-pager`. Ближайший
запуск: `systemctl list-timers node-cleanup.timer`. Запустить сейчас:
`systemctl start node-cleanup.service`.

## Базы Xray: geo-файлы и реестр

Автоматически они не обновляются. Если в новом файле не окажется категории,
на которую ссылается действующий конфиг, Xray не запустится и отключатся все
клиенты. Порядок обновления описан в `docs/SECURITY_POLICY.md`, раздел
«Обновление и подготовка к включению». Отчёт `server_update.sh` показывает,
сколько дней назад обновлялись `geosite.dat` и `geoip.dat`.

## Лимит трафика сервера

Тариф хостинга включает 5 ТБ трафика в месяц. Бот следит за ним сам:

- **Учёт.** Каждые несколько минут к трафику текущих суток добавляется трафик
  всех клиентов (VLESS и AmneziaWG). В базе хранится одна строка в сутки, без
  данных о клиентах.
- **Прогноз.** Раз в час бот строит прогноз на расчётный период хостинга.
  Модель — экспоненциальное сглаживание с затухающим трендом. Её параметры
  подбираются по истории до 8 недель так, чтобы точнее всего предсказывать
  следующие сутки. По разбросу прошлых ошибок считается верхняя граница, ниже
  которой расход окажется с вероятностью 90%. Если истории меньше недели,
  прогноз строится по среднему за сутки, а в первые часы — по сегодняшнему
  темпу. Дни периода, когда бот ещё не работал, заполняются оценкой модели.
- **Предупреждения владельцу.** Израсходовано 80%, 90% или 100% лимита;
  прогноз 90% или выше; прогноз превышения с датой, когда лимит закончится.
  Каждое приходит один раз за период.
- **Пауза пробного доступа (включается отдельно).** При 90% израсходованного
  новые пробные доступы приостанавливаются до начала следующего периода.
  Платные подписки работают как обычно. По умолчанию пауза выключена: п. 1.6
  оферты обещает пробный период после акцепта, поэтому сначала нужно дополнить
  оферту (см. ниже).
- **Команда `/traffic`.** Показывает расход, прогноз, темп, средний расход
  клиента и на сколько клиентов рассчитан лимит.

Настройки меняются через `update_bot.sh --set`:

| Ключ | По умолчанию | Значение |
|---|---|---|
| `SERVER_TRAFFIC_LIMIT_GB` | `5000` | Трафик тарифа хостинга в ГБ (1 ТБ = 1000 ГБ); `0` выключает учёт |
| `SERVER_TRAFFIC_COUNTS` | `both` | Что считает провайдер: `both` — входящий и исходящий, `out` — только исходящий, `in` — только входящий |
| `SERVER_TRAFFIC_RESET_DAY` | `1` | День месяца, когда провайдер обнуляет счётчик (1–28) |
| `SERVER_TRAFFIC_PAUSE_TRIALS` | `false` | `true` — приостанавливать новые пробные доступы при 90% лимита |

**Почему это оценка.** Бот видит трафик клиентов, а провайдер считает трафик
сетевой карты сервера. Каждый байт, который скачивает клиент, проходит через
карту дважды: из интернета на сервер и с сервера к клиенту. К этому добавляется
около 5% служебных данных. Поэтому при учёте обоих направлений бот умножает
трафик клиентов на 2,1, а при учёте одного — на 1,05.

**Что сделать один раз.** Узнайте в описании тарифа или в поддержке хостинга,
какой трафик учитывается. Если только исходящий:

```bash
bash scripts/update_bot.sh --set SERVER_TRAFFIC_COUNTS=out
```

Раз в месяц сверяйте `/traffic` с панелью хостинга и с `vnstat -m` (его ставит
`server_update.sh --apply`). Если цифры заметно расходятся, напишите — уточним
множитель.

**Как включить паузу пробного доступа.** Сначала опубликуйте новую редакцию
оферты, где в конце п. 1.6 добавлено:

> Исполнитель вправе временно не предоставлять новые Пробные периоды, если
> Узел близок к исчерпанию месячного объёма трафика, предоставленного
> хостинг-провайдером. Уже начатые Пробные периоды не прерываются.

Затем:

```bash
bash scripts/update_bot.sh --set SERVER_TRAFFIC_PAUSE_TRIALS=true
```

**Ограничения.** В учёт не входит собственный трафик сервера: обновления,
скачивание образов, резервные копии. Обычно это единицы гигабайт в месяц.
Если серверов станет несколько, прогноз сложит трафик всех серверов вместе.

# План устранения критических рисков VPN — 18.11.2026

Статус: **аудит кода и диагностического снимка; не подтверждение доступности из РФ**.
Источник кода: репозиторий, ветка main до этого изменения. Сервер: снимки
docker-inspect.json, docker-containers.txt, ports.txt, services.txt,
network.txt, routes.txt, полученные владельцем 18.11.2026.
Никакие секреты, ключи, URL пользовательских подписок и личные данные
в документ не включены.

## Главный вывод

«Неблокируемого» VPN нет. Адрес, ASN, домен подписки, сетевой транспорт,
UDP-порт, маршрут между узлами и сам доступ к международному интернету
могут блокироваться независимо. Протокол не исправляет отсутствие
альтернативных физических маршрутов.

Текущий набор технологий полезен (Hiddify/Xray, VLESS REALITY, XHTTP,
Hysteria2, RU TCP relay через WireGuard, пробник с телефона), но
**нет подтверждённой независимости exit-серверов**, а RU-2 по
docs/ARCHITECTURE.md — план.

## P0. Безопасность до расширения сети

1. Отозвать и перевыпустить токены Telegram-бота, платёжных и почтовых
   сервисов, административные ключи и токен Cloudflare Tunnel,
   попавшие в диагностический снимок. Проверить журналы использования.
2. Вынести секреты из Config.Env в Docker secrets/файлы с доступом только
   к нужным UID. **При миграции обеспечить атомарный переход**, чтобы
   не остановить оплату и активацию клиентов.
3. Держать дампы Docker и резервные копии только в зашифрованном
   хранилище, не в публичном GitHub. Не пересылать конфигурации с
   приватными ключами в открытые каналы.
4. Выяснить реальный статус AWG-агента по URL из конфигурации бота.
   Пока не подтверждены его healthcheck, порт и успешный туннель
   из клиентской сети — **не объявлять его рабочим резервом**.
5. До любых изменений сохранить проверенный откат и доступ SSH
   через независимый канал.

## P1. Резервирование от разных типов блокировок

**Два независимых выхода:** DE-1 + exit-2 в другом дата-центре, ASN и
желательно стране. Потребуется отдельный Xray/Hiddify backend,
провижининг пользователей, лимиты и тесты оплаты/отключения.
Сейчас services/provisioning.py зависит от одного HiddifyClient: просто
добавить адрес в подписку **недостаточно** для второго выхода.

**Два независимых входа:** RU-1 + RU-2 у разных операторов с
отдельными туннелями к выходам. Переносить только зашифрованный
трафик; ключи REALITY не размещать на транзитном узле.

**Транспорты (не идентичные):**
- TCP: VLESS + REALITY / Vision как один вариант.
- HTTP-подобный: XHTTP + REALITY при совместимых версиях
  сервера и клиентов. Не считать пять TCP-портов одного DE:2443
  пятью независимыми протоколами.
- UDP: Hysteria2 и AmneziaWG как дополнительные варианты,
  но часть операторов фильтрует весь класс UDP.
- Перед обновлением AWG проверить поддержку версий/параметров:
  текущий код agent.py и services/awg.py оперирует
  Jc/Jmin/Jmax/S1/S2/H1–H4, не полным набором CPS/I1–I5
  из спецификации AmneziaWG 2.0. Не менять формат существующих
  клиентских профилей без теста совместимости.

**Независимая выдача конфигураций:** HTTPS-домен подписки на отдельном
фронтенде/провайдере; аварийный HTTPS-origin с доступом к той же
логике авторизации. CDN подходит для обычного HTTPS, но не для
прозрачной проксировки произвольного VLESS/REALITY через обычный
HTTP reverse proxy. Панель администратора держать за VPN/SSH.

**Шардирование:** включать только после настройки реальных RU-2/exit-2,
сквозных проверок форматов подписок, миграции базы на RU и закрытия
возможности получить неотфильтрованную подписку панели. Включение
одного ENTRY_SHARDING_ENABLED=true не делает адреса независимыми.

## P2. Измерения и проверяемый запуск

Запускать существующий scripts/probe/vpn_probe.sh с нескольких
реальных российских операторов, отдельно от сервера. Для каждого
входа и транспорта собирать: DNS, TCP/UDP доступность, TLS/REALITY
рукопожатие, **реальную передачу данных внутри VPN**, долю
успешных подключений, p50/p95 времени, контрольный прямой запрос.
TCP reachability без пользовательского трафика — недостаточна.

Сценарии для выпуска: блокировка IP RU-1; блокировка DE-1; блокировка
домена подписки; запрет UDP; TLS handshake успешен, а payload зависает;
отказ Hiddify API при живом Xray; отключение AWG; сбой wg-vpn;
переезд клиента между мобильной и Wi-Fi-сетью.

Порядок: резервный exit-2 → ручной smoke test → RU-2 → отдельный
subscription origin → шардирование для тестового сегмента →
наблюдение и откат → поэтапное расширение. Не переключать весь
пул по одному срабатыванию одного пробника.

**Критерий:** для каждого из перечисленных отказов хотя бы один
разрешённый и *реально протестированный* путь сохраняется; доли
успеха фиксируются по оператору/дате/версии клиента. Это критерий
приёмки, не гарантия отсутствия будущих блокировок.

## Команда проверки (ничего не меняет)

На DE после получения новой версии scripts/resilience_preflight.py:

~~~sh
docker inspect $(docker ps -aq) | python3 scripts/resilience_preflight.py
~~~

Сохранённый снимок:

~~~sh
python3 scripts/resilience_preflight.py \
  --inspect docker-inspect.json --ports ports.txt
~~~

Вывод содержит только классы риска и счётчики; сами секреты не печатает.
Скрипт не заменяет внешний пробник и не утверждает, что узел заблокирован.

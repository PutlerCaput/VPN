# Cloudflare для `cyberdefency.com`

Подготовленная конфигурация на 3 ноября 2026. Владелец подтвердил зону
`cyberdefency.com` и выбрал схему: VPN и бот в Германии, платёжный сетевой
шлюз в России. Прямого Cloudflare-коннектора в рабочей среде нет. Сохранённая
привязка API-токена получила `401 Invalid API Token`; поэтому аккаунт, DNS и
Tunnel здесь не менялись. После замены токена сверяйте существующую зону и DNS
до любых изменений.

## Что получится

```text
ПК/Android ── VPN ──► Германия ──► Интернет
Бот Германия ── WireGuard ──► RU Squid ── TLS ──► api.yookassa.ru
ЮKassa ── HTTPS ──► Cloudflare Tunnel ──► RU 127.0.0.1:18080
                                        └─ WireGuard ─► бот Германия
```

Cloudflare публично обслуживает только `pay.cyberdefency.com`. Tunnel создаёт
исходящее соединение из RU, поэтому публичные RU TCP/443, 2087 и 8443 остаются
на прежнем DNAT и менять их ради webhook не требуется. Платёжное соединение
DE→ЮKassa идёт через RU по ограниченному HTTP CONNECT внутри WireGuard; HTTPS
заканчивается у ЮKassa. Карточные реквизиты клиент вводит на странице ЮKassa.
База и ключ магазина остаются в Германии. В обычной странице туннеля RU
не принимает токен/ключ ЮKassa.

Cloudflare всё равно видит и обрабатывает запрос webhook на своей сети: в нём
передаётся идентификатор платежа. Не включайте для `pay` кеширование, браузерную
проверку JavaScript или challenge. Бот считает уведомление лишь подсказкой,
запрашивает статус платежа у ЮKassa по API и выдаёт доступ только после
успешной проверки суммы и внутреннего ID.

## 1. Подготовьте зону и сохраните текущие записи

1. Войдите в Cloudflare, добавьте сайт `cyberdefency.com` и выберите тариф,
   которого достаточно для DNS и Tunnel. Если зона уже имеет статус **Active**,
   повторно менять nameservers не нужно.
2. Если Cloudflare предлагает DNS scan, сравните импорт с текущими DNS-записями
   у прежнего DNS-провайдера. Перенесите все записи, включая MX, TXT/SPF/DKIM/
   DMARC, проверки домена, CAA, SRV и имеющиеся поддомены. Не удаляйте записи,
   которые не распознаёте: пропуск почтовой или верификационной записи может
   отключить почту или другой сервис.
3. В Cloudflare → **DNS → Records** сохраните снимок списка записей до изменений.
   Для каждой записи проверьте имя, тип, значение, TTL и состояние прокси.
4. Сверьте текущие записи `panel.cyberdefency.com` и
   `sub.cyberdefency.com`. Они используются для Caddy/Hiddify Manager в Германии на
   TCP/8443; точные IP/прокси-флаги необходимо взять из уже работающей зоны.
   Сохраните их без изменений на этапе запуска платёжного Tunnel.
5. Если у домена включён DNSSEC у старого DNS-провайдера, сначала уберите старую
   DS-запись у регистратора и дождитесь её исчезновения в публичном DNS. Иначе
   смена nameservers может сделать зону недоступной. После активации зоны
   включите DNSSEC в Cloudflare и внесите новую DS-запись, показанную там, к
   регистратору.
6. Смену nameservers выполняйте у **регистратора домена**, а не в разделе DNS.
   Введите оба nameserver, которые конкретно Cloudflare назначил вашей зоне.
   Не используйте адреса из чужой инструкции. Дождитесь `Active` и проверьте
   сайт, подписку и почту, прежде чем добавлять платёжный hostname.

## 2. Защитите аккаунт и выберите режим шифрования

- Включите MFA для аккаунта Cloudflare; используйте passkey или аппаратный
  ключ, а recovery-коды сохраните офлайн. Для автоматизации создавайте отдельный
  scoped API token с минимальными правами на нужную зону; **Global API Key**
  нигде не используйте. Токены и Tunnel secret не отправляйте в чат.
- В **SSL/TLS → Overview** выберите **Full (strict)**. Не включайте Flexible.
  Обычный проксируемый origin должен иметь действующий доверенный сертификат.
  Tunnel для `pay` обслуживает edge-сертификат Cloudflare и подключается к
  локальному RU-приёмнику; Tunnel не требует публичного origin-порта 443.
- Дождитесь активного Universal SSL перед проксированием веб-имён. HSTS включайте
  только после проверки HTTPS на всех затронутых хостах; preload и
  `includeSubDomains` пока не включайте.

## 3. Создайте Tunnel для уведомлений ЮKassa

1. В панели Cloudflare откройте **Zero Trust → Networks → Tunnels → Create
   tunnel**. Создайте именованный Tunnel `ru-payment-webhook`.
2. Добавьте коннектор на RU-сервер, выбрав актуальный Linux/Debian вариант,
   который Cloudflare покажет в самой панели. Запустите connector как
   systemd-service с автоперезапуском. Token из панели вводите только в SSH-
   терминале владельца или в root-only secret-файл; не вставляйте его в чат,
   git, `.env` приложения или обычный world-readable unit-файл. Убедитесь, что
   исходящие соединения Cloudflare Tunnel разрешены firewall-политикой RU.
   Не открывайте для Tunnel новые входящие порты.
3. Для public hostname укажите `pay.cyberdefency.com`, сервис
   `http://127.0.0.1:18080`. Если в UI предлагается маршрут с путём, укажите
   `/yookassa/webhook`. Российский nginx дополнительно ограничивает доступ ровно
   этим путём и POST; остальные URL возвращают 404.
4. При создании маршрута Tunnel Cloudflare добавит целевую CNAME-запись вида
   `<UUID>.cfargotunnel.com` со статусом **Proxied**. Используйте ID вашего
   Tunnel, а не пример из документа. Не создавайте вместо неё A-запись на
   `45.138.157.65`; исходный RU IP не должен публиковаться через DNS `pay`.
5. Для hostname `pay` в **Caching → Cache Rules** задайте bypass cache для всего
   хоста. WAF не должен требовать cookie, JavaScript challenge или browser
   challenge на `/yookassa/webhook`. Не выключайте WAF для остальной зоны.
   Доступность отдельных правил зависит от текущего тарифа и панели Cloudflare.

Маршрут DNS/Tunnel не заработает до установки loopback nginx на RU и приватного
WireGuard-перехода до Германии. Подготовленный RU listener — `127.0.0.1:18080`;
немецкий listener — только приватный WG-адрес на `:18081`; бот сохраняет
`127.0.0.1:8080`. Ни один из этих файлов в production пока не установлен.

## 4. Сохраните существующие имена и верно задайте proxy-флаги

| Имя | Назначение | Решение на первом запуске |
|---|---|---|
| `pay.cyberdefency.com` | Tunnel и webhook | CNAME, созданная Tunnel; **Proxied** |
| `panel.cyberdefency.com` | Hiddify Manager UI и используемый ботом API, TCP/8443 | Импортировать текущую запись и оставить её текущий proxy-флаг |
| `sub.cyberdefency.com` | Ссылки подписок, TCP/8443 | Импортировать и оставить **DNS only**, если так работает сейчас |
| `@`, `www`, почтовые имена | Не установлено этой диагностикой | Сохранить найденные записи и proxy-флаги |
| `vpn.cyberdefency.com` | Новый прямой VPN-вход пока не создан | Пока не создавать и не проксировать |

Cloudflare HTTP proxy не передаёт произвольный VPN-трафик VLESS/REALITY или UDP
AmneziaWG. VPN-запись, когда появится проверенный отдельный вход, должна иметь
режим **DNS only**. Orange cloud для `panel` само по себе не запрещает прямое
обращение к IP DE; origin firewall при этом всё ещё разрешает 8443 из Интернета.
Перед проксированием `panel` надо отдельно защитить прямой origin и проверить,
что API бота продолжает работать. Не включайте Cloudflare Access перед ботом,
пока для серверного API не подготовлены отдельные доверенные учётные данные:
иначе проверка Hiddify Manager может начать отвечать редиректом входа.

## 5. Проверки после изменений

Сначала используйте **DNS → Records** и **Zero Trust → Tunnels**: зона должна
быть `Active`, Tunnel `Healthy`, hostname направлен на
`http://127.0.0.1:18080`. С SSH на RU проверьте, что cloudflared активен,
nginx слушает только `127.0.0.1:18080`, а Squid только на выбранном приватном
WG-адресе `:3128`. На DE проверьте, что callback listener привязан только к
WireGuard, bot по-прежнему доступен с хоста на `127.0.0.1:8080`, а у других
серверов нет этого порта в публичных правилах.

С владельческой машины разрешите DNS через `Resolve-DnsName pay.cyberdefency.com`
(Windows) или `dig pay.cyberdefency.com` и убедитесь, что публичный ответ не
содержит RU A/AAAA адреса. Затем проверьте HTTPS без платежа, например
`curl -i https://pay.cyberdefency.com/not-found` — ожидается 404, без страницы
бота и без Hiddify Manager. Для оплаты сначала нужен подтверждённый **test shop** и
отдельная тестовая БД/тестовый пользователь: реальный production ключ не
подменять тестовым. Подтверждение тестовой оплаты проверять end-to-end до
включения `YOOKASSA_EGRESS=ru_gateway` на рабочем боте.

Откат DNS — удалить только запись `pay`/public-hostname Tunnel после остановки
тестов. Не удалять `panel`, `sub`, почту и существующие записи зоны. Если меняли
nameservers или DS, возвращайте сохранённые значения у регистратора поэтапно и
проверяйте DNSSEC, иначе домен может не разрешаться.

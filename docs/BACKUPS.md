# Резервные копии: как это работает и как включить

Редакция от 8 ноября 2026. Сервер один, диск 15 ГБ, снимков хостинга может не
быть. Без копии вне сервера поломка диска означает потерю платежей, согласий
на оферту и учётных записей клиентов.

> **Хранение вне Git:** репозиторий Cyberdefency публичный. Не загружайте сюда архивы `.age`, базы, дампы Docker, `.env`, приватные ключи или распакованные каталоги восстановления. Архив age зашифрован, но его нужно хранить отдельно от исходников — в личном зашифрованном хранилище/на офлайн-носителе либо в отдельном приватном backup-хранилище. Закрытый age-ключ не хранить рядом с архивом. Файл `.gitignore` дополнительно блокирует типовые расширения резервных копий, но это не заменяет проверку перед `git add`.

## Что делается

Раз в сутки (03:20 UTC, плюс случайная задержка до 10 минут) сервер собирает
один архив и **шифрует его вашим открытым ключом** (age). Закрытый ключ на
сервер не попадает: без него архив не откроет ни сервер, ни тот, кто получит
копию из Telegram. Готовый файл остаётся на сервере (последние 7) и бот
присылает его вам в личный чат, то есть копия лежит вне сервера.

В архиве:

| Что | Зачем |
|---|---|
| `bot/bot.db` | база бота: клиенты, платежи, согласия (копия остаётся зашифрованной SQLCipher) |
| `bot/.env`, `bot/secrets/` | настройки и ключи бота, в том числе ключ базы |
| `hiddify/db.sqlite3` | база Hiddify Manager: учётные записи клиентов и их ссылки |
| `hiddify/.env`, `docker-compose.yml`, `Caddyfile`, `xray_config.json` | настройки панели и сайта |
| `INFO.txt`, `MANIFEST.sha256` | когда и откуда сделана копия; контрольные суммы файлов |

Не входит: геофайлы Hiddify Manager (скачиваются заново), образы Docker (собираются из
репозитория) и серверный ключ AmneziaWG, который лежит в томе контейнера
AWG. Пока ключей AWG у клиентов нет, это не мешает. Если начнёте выдавать
ключи AmneziaWG, добавьте том в копию отдельным шагом (скажите, помогу).

## Включить, один раз

**1. Ключ создаётся у вас, не на сервере.** В Termux:

```bash
pkg install -y age
age-keygen -o ~/age-key.txt
age-keygen -y ~/age-key.txt
```

Вторая команда создаёт файл с закрытым ключом и печатает только строку
`Public key: age1…`. Третья печатает **открытый ключ** `age1…` ещё раз: его вы
дадите серверу. Файл `~/age-key.txt` целиком (`cat`) на экран не выводите
без нужды: в нём **закрытый ключ**, строка `AGE-SECRET-KEY-1…`. Его нельзя
показывать на скриншоте, вставлять в чат и копировать на сервер.

Если `age-keygen` в Termux отвечает `too many arguments` (на некоторых телефонах
программы на Go в Termux не запускаются: ошибка даже у `age-keygen --version`),
поставьте `rage`. Это тот же формат age, написанный на Rust, ключи совместимы с
`age` на сервере:

```bash
pkg install -y rage
rage-keygen -o age-key.txt
```

Он создаст файл и напечатает `Public key: age1…`. Если пакета нет совсем, ключ
можно создать на компьютере: скачайте `age` со страницы
<https://github.com/FiloSottile/age/releases>, выполните `age-keygen -o age-key.txt`.

**2. Сохраните закрытый ключ в двух местах вне сервера.** Первое место —
менеджер паролей: один раз выведите файл (`cat ~/age-key.txt`), скопируйте
строку `AGE-SECRET-KEY-1…` долгим нажатием на экран, без скриншота. Второе —
компьютер или флешка (через кабель: `termux-setup-storage`, затем
`cp ~/age-key.txt ~/storage/downloads/`, перенесите файл и удалите его из
«Загрузок» телефона). Если копии приходят в Telegram, ключ в Telegram
(«Избранное») не кладите: замок и ключ окажутся в одном аккаунте. Потеряете
ключ, и копии станут просто шумом.

**3. Включите на сервере** (в tmux, из папки `/root/vpn-src`):

```bash
bash scripts/install_backup.sh age1ВАШ_ОТКРЫТЫЙ_КЛЮЧ
```

Скрипт поставит `age`, создаст таймер и сразу сделает первую копию. Через
минуту бот пришлёт вам файл `backup-….tar.gz.age`. В конце должно быть
`BACKUP_INSTALL_OK`. Без отправки в Telegram: добавьте `--no-telegram` (раздел
ниже), копии останутся на сервере.

**4. Проверка.** `bash scripts/update_bot.sh --doctor` теперь пишет строку
`OK backup: …`. Если копии нет или она старше 36 часов, будет `WARN` с подсказкой.

## Проверьте восстановление, пока всё хорошо

Копия, которую ни разу не открывали, не копия. Один раз скачайте присланный
файл и откройте его на другой машине, не на сервере: закрытый ключ там не должен
появляться. Из папки проекта это делает

```bash
bash scripts/restore_backup.sh backup-….tar.gz.age age-key.txt
```

Скрипт требует Python 3. По умолчанию он распаковывает архив в защищённую
временную папку вне Git и сверяет состав и контрольные суммы с манифестом.
`RESTORE_OK` подтверждает только извлечение и целостность архива. Для проверки
восстановления откройте SQLCipher с его ключом и отдельно проверьте резервную
копию панели в изолированной среде. Удалите распакованные данные после проверки.
Если `age` не запускается (см. шаг 1), скрипт использует `rage`.

**С телефона (Termux).** Проекта на телефоне нет, нужен один скрипт:

1. В Telegram откройте присланный файл, меню ⋮ → «Сохранить в загрузки».
2. В Termux один раз выдайте доступ к «Загрузкам» и возьмите скрипт с сервера:

   ```bash
   termux-setup-storage
   pkg install python
   # Сохраните актуальный scripts/restore_backup.sh из проверенной версии исходников в ~/
   ```

3. Откройте архив (имя файла подставьте своё, табуляция допишет его):

   ```bash
   bash ~/restore_backup.sh ~/storage/downloads/backup-….tar.gz.age ~/age-key.txt ~/restore-test
   ```

   По завершении появится `RESTORE_OK` и путь к проверенной папке.
4. Удалите распакованное: `rm -rf ~/restore-test`.

## Если сервер потерян

Используйте [runbook восстановления и переключения четырёх узлов](FOUR_NODE_MIGRATION_2026-11-20.md).
Сначала определите источник актуальной базы и формат резервной копии панели,
затем проверьте восстановление в изолированной среде. Перед переключением
зафиксируйте единственного обработчика платежей и план отката после первых
записей. Изменение DNS, включение бота и платёжных обработчиков выполняются
только на согласованном этапе переключения.

## Когда база на другом сервере

После переноса базы на RU (`RU_DATABASE_CUTOVER.md`) расписание и архив остаются теми же.
Меняется один шаг: вместо копирования локального файла сервер забирает актуальную базу с RU
через шлюз (`db_tool.py fetch`) и проверяет, что ключ с этого сервера её открывает. Файл
`data/bot.db` на DE в архив больше не попадает: это старая копия.

Архив содержит снимок базы шлюза. Для проверки восстановите снимок в
изолированный шлюз и подтвердите доступ с ключом SQLCipher. Порядок переключения
production описан в [runbook миграции](FOUR_NODE_MIGRATION_2026-11-20.md).

Если RU или туннель недоступны в час копии, копия не делается и бот пишет об этом владельцу,
как при любой другой ошибке.

## Копия в Telegram и закон о данных

Копия в Telegram — это зашифрованный ключом age архив с базой клиентов, лежащий вне
России. Облачные копии R2 по вашему решению отключаются именно из-за места хранения
(`docs/RU_DATABASE_PLAN.md`: копии только на RU-хранилище, R2 отключить, если юрист
не согласует). К копии в Telegram тот же вопрос юристу: допустимо ли держать за
рубежом базу персональных данных граждан РФ, если она зашифрована и у хранителя нет
ключа. Пока ответа нет, выбор за вами; оба пути работают.

- **Оставить Telegram.** Ничего не делайте.
- **Не отправлять.** Установите копии без отправки, они останутся на сервере
  (последние 7):

  ```bash
  bash scripts/install_backup.sh age1ВАШ_ОТКРЫТЫЙ_КЛЮЧ --no-telegram
  ```

  Уже установили с отправкой и передумали: `sed -i 's/^SEND_TELEGRAM=.*/SEND_TELEGRAM=0/' /etc/node-backup.env`.

  Диск сам по себе копией не считается: сервер один, поэтому раз в несколько дней
  забирайте файлы на свой компьютер или телефон в России. С компьютера (PowerShell,
  ваш ключ уже на сервере; папка `D:\backups` должна существовать):

  ```powershell
  scp root@89.125.210.172:/root/server-backups/backup-*.tar.gz.age D:\backups\
  ```

  Из Termux:

  ```bash
  scp de:/root/server-backups/backup-*.tar.gz.age ~/storage/downloads/
  ```

  (`termux-setup-storage` один раз даёт Termux доступ к папке «Загрузки».) Файл
  зашифрован, но держите его подальше от закрытого ключа age: вместе они открывают
  всё.
  `--doctor` без Telegram проверяет только свежесть файла на сервере, а не то, что вы
  его забрали.

## Что может пойти не так

- **`WARN no scheduled backup`:** таймер не включён, выполните шаг 3.
- **`WARN … no copy reached Telegram`:** копия на диске есть, но бот не смог её
  отправить. Проверьте, что бот отвечает, и запустите
  `bash scripts/backup_all.sh`: он напишет причину.
- **Бот прислал «Резервная копия не сделана: …»:** причина в тексте (не скопировалась
  база бота, нет контейнера, неверный ключ в `/etc/node-backup.env`).
- Файлы больше 45 МБ Bot API не принимает: тогда копия остаётся только на
  сервере. Для вашего объёма это не актуально, размер архива порядка мегабайт.
- Копия в Telegram хранится в вашем чате с ботом. Она зашифрована, но всё равно
  не пересылайте её посторонним.
